# Precision nutrition implementation

Bloom now has a persisted five-layer workspace at `/precision`, added alongside the existing dashboard, journal, meal planner, coach, microbiome, profile and legacy health views.

## Data and evidence flow

1. A 23andMe GRCh37 text export is parsed in the browser. Only supported calls and import metadata are sent after explicit consent. The raw file and unsupported variants are not uploaded. Placement, alleles, duplicate calls, genome build and no-calls are validated again by the API. The initial reviewed catalogue covers MTHFR rs1801133, MCM6/LCT rs4988235, FADS1 rs174547 and TCF7L2 rs7903146. Interpretation includes population and actionability limitations, original papers and technical references. This is not whole-genome, diagnostic or polygenic interpretation. Sources are curated and versioned; the application does not automatically certify new research or reinterpret arbitrary variants.
2. Owned, completed structured microbiome abundance reports can be selected. Reported taxa, experimental model indices, entered laboratory metabolite measurements and research hypotheses remain distinct. Only reports containing validated structured abundances enter the precision workspace; legacy demo profiles are excluded. Genotype-to-microbial-pathway links identify uncertainty rather than inventing interactions, organism deficits or flux. Metabolite entries include specimen, units, method, laboratory and date; their values do not automatically become supplementation targets.
3. Dated LDL, ApoB, triglycerides, HDL, ALT, AST, GGT, glucose, HbA1c, B12, vitamin D, ferritin, folate and homocysteine results retain original units and laboratory intervals. Supported alternative units are normalized for comparisons. Flags use the entered laboratory range, not diagnostic or individualized treatment thresholds. Results older than 180 days remain in history but do not drive current laboratory flags. Newer results supersede older results for current ranking.
4. Recent laboratory context contributes more than common variant context to transparent rule priorities. Seven individually ranked foods and fifteen complete recipes expose nutrient contributions, sources, pathway hypotheses and uncertainty. Food category restrictions, dislikes, dietary pattern, cooking-time and sensitivity apply before ranking. Allergies are recorded and ingredient-name matching also applies, but this does not certify allergen safety or preparation/cross-contamination. Food contribution labels are qualitative; database-derived nutrient quantities remain in the existing meal-analysis workflow. Genetic lactase findings produce tolerance context, not automatic dairy exclusion. Generic goals remain editable; unknown goals are retained without fabricated dedicated rules. Existing butyrate/diversity preferences also contribute. Exact response magnitude is not predicted.
5. Named plan snapshots retain the evidence version and recommendation/source/input references. Users can record linked adherence, body weight, body fat, waist, bloating, energy and notes without zero-filling unmeasured fields. Repeat biomarkers are compared only across different dates, matching laboratory and known method, and compatible fasting context when relevant. Observed changes are not causal attribution. The workspace also shows existing meal symptom records and 28-day known macro/micronutrient totals with coverage; incomplete food logging cannot diagnose a nutrient deficiency.

## Supplement handling

Only current supported laboratory flags create B12, vitamin D, folate or iron-status *assessments*. No variant automatically triggers supplementation. All doses are null: these are review items, not prescriptions or product recommendations. Missing safety confirmation, pregnancy context, non-adult/unknown age and recorded medicines/conditions/supplements trigger review blocks. Even an otherwise complete adult profile requires clinical assessment for replacement. Folate prompts B12 review; iron prompts assessment beyond ferritin; vitamin D prompts review of calcium, renal context, total intake and interacting medicines. The history screen is not an exhaustive drug/supplement interaction database.

Adult rules are withheld for unknown age and under-18 profiles. Children can record inputs and observations but require an age-appropriate validated nutrition pathway before personalized ranked outputs. Pregnancy and complex disease also require individual clinical oversight.

## Persistence, privacy and API

Apply `migrations/0002_precision_nutrition.sql` after the earlier additive migration, or review the corresponding schema with `npm run db:push`. The migration adds `precision_profiles` and `precision_records`, preserving all existing tables and rows.

Set `PRECISION_DATA_KEY` to a securely generated, base64-encoded 32-byte secret. For example, generate it locally with `openssl rand -base64 32`, place it in a secret manager, and keep it out of source control and logs. Precision context and payloads use AES-256-GCM with account-bound authenticated data. Missing/invalid keys fail closed when storing or reading encrypted data. Retain the key securely with backups; key rotation needs an explicit re-encryption migration, and losing the key loses access to those records. Application encryption does not replace HTTPS, secure sessions, database access controls or backup policies.

- `GET /api/precision`: personal report, selected owned structured sample via optional `sampleId`, current/historical markers, predictions/measurements, food/meal priorities, supplement assessments, plans, check-ins and recorded nutrient coverage.
- `PUT /api/precision/context`: validated goals, medicines, supplements, conditions, allergies, age/pregnancy context and safety-history acknowledgement.
- `POST /api/precision/records`: validated genetics, lab, measured-metabolite or check-in payload; client-supplied ownership and conclusions are rejected.
- `POST /api/precision/plans`: server-computed plan snapshot, never a client-supplied recommendation list.
- `DELETE /api/precision/records/:id`: account-scoped removal. Removing a source clears derived plans; deleting one plan does not delete other plans.
- `DELETE /api/precision`: explicit confirmation header clears that account's precision inputs, profile and precision plans. Existing meal journal and microbiome source reports are retained and have their own existing flows.

All precision API responses use `Cache-Control: no-store`. Sensitive response bodies are excluded from request logs. These routes never transmit genetic, lab or health-context inputs to an AI provider. Existing optional AI meal parsing/ranking remains governed by its existing user opt-in.

## Verification and remaining product development

Tests cover import integrity and strand conventions, original/normalized units, invalid and stale data, missingness, weighting, dietary eligibility, no genotype-triggered supplements, safety blocks, measurement/prediction separation, comparable biomarker trends, account isolation, plan references, deletion confirmation and authenticated encryption. Browser flows exercise the real precision route handlers using a test persistence adapter; an embedded PostgreSQL (PGlite) integration test additionally applies the actual additive migration and verifies encrypted storage, upserts, isolation and deletion transactions. Production database and provider credentials are not used.

The complete five-layer workflow is now implemented as a bounded first version. It is not a comprehensively validated precision-treatment engine. More variants, biomarkers, foods and goals require reviewed catalogue additions; new research needs expert appraisal, conflicting-evidence handling and maintenance. Comprehensive medicine interactions, automatic laboratory/PDF adapters, raw sequencing classification, harmonized real cohort distributions, unrestricted meal generation and prospective clinical validation remain separate work. Genetic and microbial associations must not be presented as proven personal treatment effects.
