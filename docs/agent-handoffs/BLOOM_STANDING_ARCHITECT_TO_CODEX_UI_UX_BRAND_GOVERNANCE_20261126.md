## 2. UI execution mandate: User UX and Brand specs first

For every **selected UI screen build or significant refactor**:

1. **Read both original specialist specs**—User (UX) Spec and Brand (UI/Design System) Spec—plus approved owner visuals for *that screen* before changing layout. Translate into actual page component acceptance: above-the-fold primary task, visible hierarchy, navigation, mobile/desktop breakpoints, progressive disclosure, copy budgets, token use, empty/error/loading states and reachable support actions. Neither spec is an optional aesthetic afterthought.
2. **Progressive disclosure as the default:** one clear primary action and meaningful first-screen information, secondary details behind existing drawers/bottom sheets, tabs, expandable sections, or contextual information disclosures as the relevant UX spec directs. Preserve source fidelity and full detail access; **do not** dump raw logs, long mappings, audit receipts, telemetry, trace/debug keys, duplicate forms or multiple paragraphs of uncertainty/disclaimers into primary consumer screens. Put justified technical detail in accessible intentional details/debug/source views. Do not hide truly critical reviewed safety messages behind disclosure.
3. **Brand consistency:** reuse established app tokens, typography, spacing, color/contrast, page composition, approved illustrations and reusable components; preserve high-quality legacy UI and original science artwork rather than replacing with a generic admin table or raw form stack. Responsive layouts are designed, not merely CSS-squeezed.
4. **Truthful educational/wellness copy:** concise, calibrated and source-specific. No unsupported clinical, diagnosis, injury, recovery, treatment, biomechanics, physiological participation, personal inference or causal claims. Known zero, unrecorded, unknown, provisional identity and correction remain distinct. Where qualifying copy is necessary, design it *short, contextual and progressive*, not an overwhelming disclaimer wall.

## 3. Mandatory rendered viewport acceptance for key UI work

Before reporting a **key user-facing screen** or substantive refactor ready for handoff, **capture and inspect actual rendered screenshots at `390×844` mobile and `1440×900` desktop**, covering at least initial state, open/active drawer or selected item, and relevant secondary tab/disclosure. Verify all applicable states in both viewport sizes; use minimal appropriate coverage for screens without a drawer/tab and mark those states `NOT_APPLICABLE` with explanation. Look specifically for cramped/squashed layout, unreadable charts, text walls, clipped panels, overflow, hidden/buried primary actions and broken mobile interaction. Correct material defects before marking `UI_ENGINEERING_VERIFIED`.

Record screenshot locations or local artifact reference, exact branch/source SHA, key view/state, genuine render environment and failures/fixes in the selected task's normal receipt. **Do not claim screenshot or screen-reader approval from source/static inspection or a prior unrelated checkpoint.** If no real browser/image capture is available, state `VISUAL_VERIFICATION_NOT_TESTED` and keep handoff acceptance qualified. Continue keyboard/focus/list/ARIA, themes, zoom, reduced motion and device/accessibility tests required by the specific feature. Screenshots are not themselves independent WCAG or physical AT certification.

This targeted **key UI** screenshot requirement supersedes the old blanket guidance in `AGENTS.md` that screenshots need not be routine. It does **not** require an expensive full screenshot campaign for code-only, security, backend or tiny invisible fixes.
