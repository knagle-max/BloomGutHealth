# Bloom v0.6 — Core vs Advanced: Binding Codex Execution Classification
**Date:** 2026-11-14 | **Status:** Architect-approved implementation **prioritization**, not a new scope authorization or verified release.
**Owner directive:** Divide existing approved v0.6 into **Core** (genuinely useful everyday product) and **Advanced** (higher-complexity scientific intelligence and professional capabilities as dependencies mature).
**Controlling:** `NEXT_ACTIONS.md`, `docs/operations/V06_DEPENDENCY_BACKLOG.md`, `docs/architecture/V06_HANDOFF.md` plus all earlier approved owner amendments. **This is a priority and acceptance crosswalk, not a replacement roadmap, separate architecture, new approval stage or cancellation of specialist requirements.** Codex is sole engineer; normal safe development runs without interim owner approval.

## 1. Classification rule
**Core = must be genuinely usable with ordinary goals, owned food/activity/lab observations and source-grounded reviewed nutrition**, even if no genetics, microbiome, wearable, LLM, Python solver or professional coach exists. Build robust private source/correction/consent/goal/action systems first. A feature that conveys research-only uncertainty but cannot support an ordinary decision does not substitute for the Core user-value gate.
**Advanced = source-, scientific-, privacy-, rights- or technical-dependency-gated personalization and scientific expansion.** Development, isolated synthetic/reference tests and separately authorized super-user research visibility **may proceed concurrently** with Core when they do not consume the critical path, introduce new public personal effects, weaken source/safety/privacy gates or block the base app.
**Shared foundations** (provenance, controlled source acquisition, AI-tier evidence/claim lifecycle minimum, security, method/units, data contracts and bounded scientific coverage reporting) are **Core to the extent needed for safe ordinary outputs**, while comprehensive autonomous literature pipelines and model research expansion are **Advanced**.
**Feature-gated—not entire-project-gated:** External licence/clinical/consent blocks suspend affected functions only; approved unaffected Core work continues. Any release must be truthful about actual implemented/validated user-facing scope. No new owner checkpoint.

## 4. Codex scheduling and queue hygiene
- **Priority order:** reproducible current safety/source P0 → Core C1 Today/Food and C2 panel Response **in parallel** with C4 targeted reference ingestion → C3 practical nutrient coverage, then C5 action/feedback/polish → C6 validation. Dynamic current-head verification takes precedence over stale commit descriptions. Resolve actual blockers per feature, not global.
- **Parallel Advanced budget:** independent A1 synthetic/reference Python, scoped A2 source discovery/review proof and model registry metadata may progress when a safe separate workstream exists; no displacement of C1/C2/C4 test/merge cadence or speculative major model hosting.
- **Preserve source integrations:** 35 approved source IDs retain assignments and optional/research/rights states; Core only requires relevant high-value source slices with verifiable user outcomes, not premature ingestion of every candidate.
- **Shared infra never cloned:** no second AI engine, food DB, lab ledger, research graph, safety evaluator, consent engine, user study UX, or competing backlog. Reuse `NEXT_ACTIONS.md` as sole active queue, `V06_DEPENDENCY_BACKLOG.md` as ordered dependency evidence, `V06_HANDOFF.md` as canonical evolving architecture.
- **Branch policy:** existing approved preview/dev branch and existing isolated Food/UI branches; inspect latest HEAD and actual commits before editing; no blind merges or new main release.
- **Classification status:** `architecture approved`, `code present`, `source acquired`, `rights cleared`, `evidence approved`, `tested`, `hosted`, `user validated` are separate. No fake release completeness claim.

## 5. Final functional user acceptance before Core considered complete
1. Goals-only authentic user sees one feasible actionable and understandable proposal, no unnecessary omics or lab requirements.
2. User with breakfast/lunch and preferences gets **specific grams/portions** dinner and editable substitutions; save/reload and consumed status are correct; no seafood/other excluded foods.
3. All 30+ user-provided lab rows remain present; relevant lipid/liver/glycaemic/CBC/iron evidence and uncertainty are applied across report and source-consistent history, with an actual safe next step. No single-marker tunnel vision, clinical overreach or invented attribution.
4. Normal user can monitor routine change→outcome while preserving multiple goals and avoiding deliberate experiments, treatment changes or extra tests for the app.
5. Real source snapshots (not just docs or local mock) produce consumed nutrient and lab mappings with known/unknown values, source rights/revisions and outage fallback.
6. Safe consumer app functions if every optional cloud AI, shadow solver, DNA/microbiome or device source is offline; no data leak through normal or restricted APIs.
7. Scientific and user testing distinguishes verified, pending and absent, with exact commit SHA/CI/API/database/browser/Render evidence and independent real-human tasks where done.
