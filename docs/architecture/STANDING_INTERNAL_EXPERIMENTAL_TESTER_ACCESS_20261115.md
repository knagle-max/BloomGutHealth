## Source evidence: why the current expiry happens
On current `enhance/bloom-experience`, `server/capability-access.ts` `grantSchema` requires `expiresAt: z.string().datetime({offset:true})`; `internalPreviewGrant` rejects `+new Date(grant.expiresAt) <= now`. It reads primary JSON `BLOOM_INTERNAL_TESTERS`, optional `BLOOM_ADDITIONAL_INTERNAL_TESTER_GRANT`, and still requires exactly one matching valid grant, current `RENDER_SERVICE_ID`, `BLOOM_EXPERIMENTAL_ENVIRONMENT=isolated-synthetic`, territory, `bloom.dev.preview`, explicit scoped UI-preview grants and global kill-switch not active. The raw configuration **was not inspected or changed** by this architecture note, so the exact Nov 22 timestamp is inferred from the owner-quoted deployment message, not directly verified in Render secrets.
Existing preference persistence stores `enabled` and a **fingerprint over the full serialized grant**. A naive removal/change of `expiresAt` would change the fingerprint and make the existing ON preference look OFF. Reconcile that safely.

## Design: optional bounded vs standing eligibility, explicit only
1. **Grant types:** preserve current expiring grants for temporary testers, but permit a **distinct explicit `standing-internal` grant** with no expiry date (`expiresAt` absent/null only for that typed grant). Unknown/malformed/untyped grants still fail closed; no blanket permit based on usernames, email domains, presence of toggle or a browser cookie.
2. **Scope:** standing status limited to documented internal testing account identity on this service and approved territory/environment. Required `userId`, `grantId`, `serviceId`, `reviewReference`, scoped allowed capabilities and `uiPreview` remain mandatory as applicable. No `bloom.dev.preview` self-enrolment and no automatic execution grants for restricted features. Do not use a public setting to confer standing status.
3. **Revocation:** global `BLOOM_EXPERIMENTAL_KILL_SWITCH`, per-account grant removal/suspension, service/territory changes, role/permission/consent revocation and feature-specific kill switches remain effective immediately. Ensure account switch clears restricted state. Standing grant means **revocable, not irrevocable**.
4. **Fingerprint/preference:** retain fingerprint verification to detect **material scope change** and enforce fail-closed authorization. For a compatible update from expiring grant to standing grant for **the exact same account, stable grant identity, server/service scope, allowed feature set, purpose, territory and preview restriction**, preserve the saved ON preference through an explicit audited one-time authorized migration/rebind; if assurance of same grant/scope isn't available, show a truthful one-time ON toggle (not a weekly renewal). Changing permissions, user, environment or kill switches must not preserve stale unauthorized access. Test rebind races and cross-account IDs.
5. **Source of configuration:** update the **actual authorized Render environment grant for Tester1** from `expiresAt: 2026-11-22...` to explicit standing type, then deploy/verify at exact SHA. Do not invent the user ID, manipulate other testers, print environment secrets in logs/docs, or claim this configuration was updated if not. The amendment isn't effective until both code and runtime grant are migrated.
6. **Public release vs internal:** standing internal tester access doesn't authorize public launch, clinical advice, sensitive research, independent model execution, data sharing or third-party API calls. Use current `effectiveCapabilityDecision`/capability service and feature-specific restrictions; no duplicate grant database.
7. **UX:** settings can label the account “Internal tester · Standing access” or simply show availability if account is eligible; do not display an expiry countdown for standing grants. Remain truthful for expiring external testers and when eligibility is removed. Feature-only restrictions are shown independently from account expiration.
