# Bloom — Chief Architect binding decision: Universal Biological Report Management & Deletion
**Date:** 2026-11-05 | **Implementation owner:** Codex | **Architect status:** APPROVED P0 immediate repair + staged P1 unified management UX; NOT implemented or release-tested by this decision.
**Controlling source:** Product Owner's “Bloom — Chief Architect Directive: Universal Biological Report Management & Deletion” provided on 2026-11-05. Its original eight sections and specified 15 regression scenarios govern where compatible; this document resolves priority, data boundaries and execution.

## 1. Reviewed current branch and proven immediate defect

At architect inspection of `enhance/bloom-experience`, `client/src/components/ViomeSavedContext.tsx` contains `Delete this Viome source` **inside a collapsed details block beneath `Source relationship`** and conditionally depends on extracting `viomeSource(sample.structuredData)`. A generic saved microbiome history record that lacks recognized current Viome structured metadata can therefore lack a visible manage/delete route. This is a **P0 account data-control defect**, not an advanced science or interpretation issue. The existing control calls an owner-scoped `DELETE /api/microbiome/reports/:id`, invalidates related caches and preserves companion semantics for recognized Viome. **Codex must inspect current endpoint authorization, supported legacy storage, and related UI before reuse**; the presence of a successful current-Viome deletion call does not demonstrate a safe universal deletion contract.

**Immediate first task (P0, preempts cosmetic UX and is independent of private PDF fixture access):** For EVERY user-owned saved microbiome report, including legacy, manual-source, qualitative, quantitative, PDF, JSON/CSV and historical unsupported-for-interpretation records, show a conspicuous `Manage report` or `Delete report` action in the selected report header/history detail. No dependency on `viomeSource`, a companion/specimen relationship, current assay validity or whether Bio interpretations exist. Show source type, original available biological collection/report date and status; **never expose prohibited client/test/sample IDs or original unredacted Viome PDF metadata**. Explicit scoped confirm, owner-bound deletion, reliable success, appropriate remaining-report/empty-state navigation. If any record lacks a true report source but is independently saved manual observation, offer the appropriate **Delete result** action with truthful scope; do not label a collection of unrelated records as one report or delete data beyond one selected source.

**Priority vs Viome PDF:** This is a newly demonstrated P0 privacy and user-agency defect affecting already saved records. Fix **first as a bounded vertical slice**; then immediately resume the existing P0 layout-aware Viome PDF importer compatibility work, which must not be considered complete on surrogate PDFs alone. Do not turn the initial delete control into a precondition to building the entire P1 Manage Reports interface.

## 2. One reusable lifecycle service, four distinct scopes

Use existing canonical source ownership, observation provenance, immutable version/correction history, and existing deletion routes/transactions as the single source of truth. Map supported legacy sources into it without a second deletion subsystem.

- **Delete result:** remove one exact laboratory or other independently owned observation plus exclusively dependent revisions/projections, respecting shared sources and audit/retention policy; no accidental deletion of sibling observations. Existing immutable correction history remains intact until explicit result deletion.
- **Delete report:** remove one user-owned report/source and only observations, revisions, corrections and derived outputs owned exclusively by that report. A surviving companion PDF/document, independent manual observation, unrelated report, preferences and food journal must remain. If any item is referenced by another independently retained source, unlink rather than indiscriminately cascade.
- **Delete selected reports:** verified explicit selected IDs within the same authorized account, preview exact affected counts/source types; perform as a coherent atomic operation or a safely retried batch that does not misrepresent partial success; prevent foreign IDs, duplicates, stale and concurrent mutations.
- **Delete all reports in category:** exactly one of Microbiome, Bloodwork or Genetics, based on the canonical category and owned source set, with category-scoped impact. **Do not equate category deletion with the existing Delete all precision data**—retain that wider operation's current behavior and accurately describe its affected categories and plan impacts.

**Genetics active-state rule:** Delete selected historical or active genetic source without silently making an older dataset current. If active source is removed, present a clearly declared `No active genetics dataset` state pending deliberate user selection; existing versions remain individually accessible if not deleted. Respect sensitive consent, effective permissions, derived highlights and stale cache invalidation. A true user-approved successor activation would be a **distinct explicit user action**, not automatic fallback.

**Bloodwork rule:** The report/source/collection/import grouping must be grounded in existing receipts and occurrence/provenance, not inferred by matching date alone. Delete result must remove dependent value/date/unit correction branches. Deleting a whole source removes its exclusively owned observation records but not independent labs or manually added biomarkers.

**Microbiome rule:** Legacy and manual imports, source-quantitative and source-qualitative findings are eligible. Viome companion reports are separately owned documents: delete one, preserve the other's independent biological findings and make their relationship safely unlinked; do not use original vendor sample/test identifiers to decide relationship. An imported qualitative source cannot become quantitative by deleting another source.

## 3. Safe deletion and confirmation contract

- Every confirmation must disclose selected source/report count, observation count **only when reliable**, which kinds of derived recommendations/trends/highlights/plans will be invalidated, what other reports/categories remain, whether the action is reversible, and whether any historical audit/backups persist under retention policy. Confirm **before** irreversible deletion. Never make inaccurate “deleted from every backup instantly” claims.
- Enforce current authenticated owner and per-record authorization **server-side**, not merely visible UI. Prevent route ID enumeration/leakage and cross-account cache/data access. Handle stale, concurrent import/edit/delete with a consistent transaction boundary, source-version matching/preconditions where available and safe retries/idempotency. A lost response must not cause accidental extra deletion; only acknowledge actual committed deletion or authoritative already-deleted state for the same owned operation.
- Explicitly invalidate all dependent current projections: Gut reports/selected source, Biology summary, Food suggestion opt-in/source badges, recommendation caches, Progress trends, genetics personalized highlights and report selection, calculated lab insights, planner/saved plan links and relevant client-side caches. Rebuild from **remaining canonical sources**. Do not delete unrelated meal logs, athlete records, profile settings or independent health observations.
- Respect existing encrypted storage and data retention. If backups/log policy requires later eventual erasure, tell user accurately; no raw sensitive payload in error logs, redirects or telemetry.
- When a report has unsaved review/correction work, cancel/deletion flow must not silently discard drafts; correctly distinguish deleting a saved report from discarding an uncommitted import.
- Any legacy record that cannot safely be mapped to a report ID should expose an honest scoped action and a precise technical blocker rather than disappear, or receive unsafe blanket deletion.

## 4. Discoverable Manage reports UX — P1 staged after immediate fix

Add **My Biology → Manage reports**, also linked from **Profile → Privacy & data controls**. Do not create a parallel navigation system. Use existing styling, accessible list/actions, roles and source rows.

**Microbiome:** report list, individual delete, select multiple, delete all category.
**Bloodwork:** original source/import event/known collection context, individual observation delete, report-level delete, selected reports, delete all category.
**Genetics:** source import/snapshot list, current-active label, individual/historical/active deletion, selected imports, delete all genetics, explicit no-active state after active-source deletion.

Each list row should show report type/source, known collection date, import date, saved/current state, and honest observation count if reliable; View details and **Delete report** visible. Put category-wide deletion in a visually separated destructive section. A user with no records sees a clear empty state; a user with many has accessible selection and review, not silent mass deletion. For mobile/keyboard/VoiceOver ensure focus restoration, destructive dialogs, typed or checkbox confirmation proportionate to scope, 320px/200% zoom, safe pending and retry states.

## 5. Acceptance and implementation sequence (P0 first, no governance loop)

**P0 first commit:** inspect current report list/selection, legacy record shape, current `DELETE /api/microbiome/reports/:id` and its database/cascade/authorization behavior. Implement a visible header-level delete on **all** existing report paths, source-independent generic deletion contract or reuse safe current endpoint, and reselect remaining report/empty state. Verify with **persisted synthetic legacy** and current Viome data, companion pair, quantitative, manual, duplicate/retry, foreign/stale requests and reloaded UI; fake-only React component tests are insufficient.

**P0 category foundations:** Once immediate delete works, ensure Genetics active/historical and Bloodwork report/result source-bound deletion services support individual actions, correct immutable revisions and no unrelated data loss. Use existing safe operations, no speculative migration or duplicate store. Test persisted state, source/projection invalidation, account isolation and consistent API response.

**P1 additions:** Add select-multiple and category-wide actions with explicit precise impact review, then single My Biology Manage reports destination and Profile privacy link. Keep these coherent staged tasks, not a prolonged all-at-once redesign. If immediate P0 is working, resume the independently open Viome PDF P0 layout fix rather than letting a large management programme displace it.
