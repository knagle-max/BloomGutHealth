## 4. Lightweight jumping-between-tracks discipline — adopt now

**Status tag (one per touched track, coarse summary only):**
- **PROVEN** — specific behavior with actual test receipt, exact SHA, scope/platform; never equate unit pass with hosted/science/clinical validation.
- **IN FLIGHT** — actively edited, partially qualified, known gaps, failing test or pending review. No UI/marketing text implies complete.
- **EXPLORATORY** — optional isolated spikes such as Ollama/local AI, new model challenger, stylistic concept. No deployment dependency until usefulness/safety tests.
Use `BLOCKED` as a *separate reason/status* if needed, not as a substitute for the three maturity states. A subsystem may have proven deterministic math and unproven AI interpretation concurrently; tag the *claim/slice*, not the entire feature as one green item.

**Seam guardrails (contract before polish):** Before touching any UI/backend, private/public or deterministic/AI boundary, name the invariant, existing owner file, typed schema, failure/unknown state, minimal negative regression and privacy/scientific release gate. A small validated interface beats speculative integration. This is a lightweight checklist in the existing task/commit record, **not a new architecture phase or approval committee**.

**2-minute breadcrumb on context switch:** At a meaningful switch, append at most 3 brief fields to the *existing* `DEVELOPMENT_LOG.md` or existing execution checkpoint (do not create a second task board):
```
Track / maturity: <P1 investigation | P2 science | UI | private mode | local AI> — PROVEN / IN FLIGHT / EXPLORATORY
Changed + proof: <files/commit/check and its scope>
Open + next: <unfinished or blocked item; smallest safe next test/action>
```
Only log meaningful change, context-switch or handoff; do not force hourly notes, rigid sprint ceremonies, time-tracking or repeating full summaries. Keep case data, credentials, private prompt/results and secret-bearing file paths outside Git. Use `NEXT_ACTIONS.md` for priority, `DEVELOPMENT_LOG.md` for work evidence, existing checkpoint for active local state and `BLOCKED_USER_INPUT.md` only for owner-dependent blockers. Prefer one active integration owner, bounded branch/test scope and an exact SHA receipt rather than many overlapping experimental changes.

**Adaptive work selection:** It is acceptable to switch UI, biological reasoning or local AI when a high-value task is unblocked, user-directed or makes reusable progress. Before switching, verify status and seam tests; after switching, leave breadcrumb. Do not jump over critical privacy/source regressions or owner-paused deployment. The science-first priority is a compass, **not a waterfall**; protected user data and scientific claim authority are invariant. Avoid declaring a mature track unfinished simply because unrelated exploratory work is ongoing.
