# Bloom — Chief Architect Codex anti-loop execution policy
**Date:** 2026-11-05
**Scope:** All Codex sessions on `enhance/bloom-experience`; PR #1 and existing authorized Render review deployment.
**Authority:** Chief Architect task-selection and acceptance integration. Does **not** waive safe data, privacy, clinical, third-party, or actual deployment gates.

## Confirmed evidence and limits
Current `NEXT_ACTIONS.md` carries multiple consecutive historical producer/reader/source-unit checkpoints with reported broad suites in the 530–547 range, duplicate "publish candidate" and "continue next unit gap" instructions, older progress updates below current instructions, and unresolved external acceptance. `PERSISTENT_TASK_INDEX.md` dates to October 24 while v0.5 scope changed multiple times. These records indicate **risk of repetitive micro-hardening and task-selection drift**; they do NOT alone prove Codex runtime is in an infinite loop. The repository-wide empty commit search surfaced historical Replit commits and is **not** an authoritative current branch timeline. Codex should use exact current branch checkout/git log and current CI/Render status instead of assumptions from a global search.

## Execution policy (binding and effective immediately)

1. **One active task / one authoritative queue.** At session start identify current branch SHA and take the top **uncompleted actionable** work item from the current `NEXT_ACTIONS.md` top decision block. `PERSISTENT_TASK_INDEX.md`, `ACTIVE_EXECUTION_QUEUE.md` and old sections of `NEXT_ACTIONS.md` are reference/evidence, not competing task selectors. Superseded older instructions must not override this directive. Architect controls new scope; Codex owns engineering.
2. **Task definition before editing.** Record one stable task ID, user-visible goal, affected existing code, minimal acceptance scenarios, current implementation baseline, expected touch boundaries and **exit condition**. Prefer working complete vertical user journeys over tiny subsequent source/provenance refinements; reuse existing code, avoid duplicate registries.
3. **Bounded effort and regression.** For each development slice: relevant focused tests + typecheck/build; run full suite once at the release checkpoint or when cross-cutting changes justify it. If a focused regression fails, fix and rerun that group; don't repeatedly run an unchanged full 500+ suite after documentation, copy, or a small isolated change. Follow repo CI if it automatically runs broader coverage. No suppression of required security tests.
4. **Two-attempt rule for same blocker.** After **two materially different, failed approaches** to the same specific problem or the same failure recurring without new evidence, write a concise diagnosis (exact error, reproducer, attempts and why) and mark `TECHNICAL_DEPENDENCY`, then choose the next independent approved task. Revisit only after new evidence/changed condition. Do not endlessly tweak guardrails or source fields without observed user harm.
5. **Do not reopen completed work** without (a) a reproducible regression at current HEAD; (b) a newly approved explicit requirement; or (c) a demonstrable privacy/data-integrity/medical-safety failure. Already tested source-value/unit/correction slices are not a perpetual queue of ever-finer edge cases. New low-severity cases go in stabilization with severity and affected real user journey; do not delay core launch.
6. **Publication checkpoint.** Do not announce a new "candidate" repeatedly. When focused validation and impacted source/test checks pass, make a coherent commit, push on the authorized branch, verify current CI status and applicable existing Render preview SHA once. If CI/Render is temporarily unavailable, mark `IMPLEMENTED_PENDING_DEPLOY_VERIFICATION` and move to independent work. Avoid repeated redeploy/CI polling or claiming a different SHA is live.
7. **Completion means user value.** An item is `IMPLEMENTED_AND_TESTED` once its specific end-to-end user journey, data correctness, account boundary, relevant negative tests and build evidence pass. Independent physical iPhone/VoiceOver, human study, clinician signoff or externally licensed activation get **separate acceptance statuses**; they do not force endless code amendments or prevent unrelated progress. Never mark all requirements or launch fully complete by fiat.
8. **Source handoff and blocker handling.** Previously resolved owner decisions, original 43 criteria, recovered Genetics §5A, and private Viome fixture presence are not repeated research tasks. Native PDF parser may be built and tested against synthetic PDFs while private real-layout acceptance is held. Render DB binding is a narrow read-only runtime probe task, not a reason to keep rewriting local migration plumbing. No original private PDFs, PII, live database writes, new provider charges or real data exposure.
9. **Dependency-aware task order (next three vertical outcomes):** (A) finish/publish *currently genuinely unfinished* Food original-entry→review→one confirmed save→reload if demonstrably incomplete; otherwise close it and stop revisiting units. (B) native Viome PDF upload→privacy-safe parse→review→save against synthetic fixtures, then separately exact real-PDF secure acceptance. (C) Genetics source-eligible claim and first useful relevant findings card(s), preserving whole 17-domain explorer, with evidence/consent gate. Current supported activity/Today blocker may preempt only on observed P0 breakage. Don't spend repeated sessions on asset-only source transports or old 150–250 numeric catalogue quota.
10. **Version transition:** Once core actionable v0.5 items pass their executable criteria or are narrowed to factual `EXTERNAL_ACCEPTANCE`/`DEFERRED`/`TECHNICAL_DEPENDENCY`, record v0.5 **engineering milestone** distinctly from v0.5 **release acceptance**, and begin approved independent v0.6 user-value work. Do not wait for an impossible-to-complete external gate to move to a safe other phase.
11. **Compact checkpoint format** (replace long chronological streams): `HEAD | one active ID and exit condition | completed IDs + exact SHA/test/deploy | open actionable next 3 | external approvals separately | new blocker with retry evidence`. Archive old detailed progress to dated docs instead of appending endless overlapping "current" blocks. After each successful slice, **actually continue to the next eligible** task rather than stopping just to announce completion, within the active session limits. Codex cannot work asynchronously after its session ends.

## Distinct prohibitions
This policy does **not** authorize deleting valuable tests, skipping failing checks, bypassing reviewer/legal/medical gates, modifying main, making paid calls, changing deployment secrets, writing to unidentified Render DB targets, committing real Viome data, or changing production schema without authorization. Escalate new high-risk issues immediately; leave otherwise independent work moving.

At next Codex checkpoint expect: current branch head, a single chosen task with concrete end-to-end exit, a short list of no-longer-actionable repeated tasks and their evidence, selected priority from the ordered list, one successful focused verification/build, commit and linked CI/Render SHA where possible. **Do not substitute another governance/reconciliation document for code work.**
