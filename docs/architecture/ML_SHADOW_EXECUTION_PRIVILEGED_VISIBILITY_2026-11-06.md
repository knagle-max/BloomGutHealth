# Bloom — Owner ML Directive: Full Shadow Execution + Privileged Development Visibility
**Date:** 2026-11-06 | **Status:** APPROVED v0.6 architecture and implementation. Not a deployed implementation, public release or regulatory clearance.
**Supersedes:** Any inference that medically adjacent ML development stops at a disabled UI or a mock adapter. Preserve `PYTHON_ML_RESTORATION_AND_MOLECULAR_EXPANSION_DECISION_2026-11-06.md` and the owner's active two-track Python implementation direction.

## 1. Exact owner intent and controlling safety interpretation
The Product Owner wants Bloom ML to **operate and help ordinary users as much as defensibly possible**, while medical-device-borderline, clinically consequential or not-yet-validated models **continue to execute and be evaluated in shadow**. Results must not be visible/actionable to general users, but an appropriately **server-authorized privileged tester** may inspect eligible experimental outputs through the existing Profile **`Show development features`** toggle.

**Architect approves THREE separate controls, not one switch:** 
1. `COMPUTE_SHADOW` — server-only independent evaluation of candidate model computations; production/user data only if independently permitted by purpose-specific consent, lawful handling, rights, deployment authorization and security. Otherwise use synthetic/reference/isolated replay. **Turning OFF the UI toggle does not itself turn off properly authorized shadow evaluation**, but revocation of data permission/consent DOES.
2. `VIEW_RESTRICTED` — only server-granted account/capability/territory/environment/expiry may retrieve suitable experimental result; the existing `Show development features` toggle merely opts an already authorized tester into **display**. It never grants research execution, access to others' data, medical advice privileges or use of sensitive personal datasets. A public user cannot enable via devtools/API flag.
3. `APPLY_TO_USER` — an entirely separate **science/evidence/intent/use/clinical/regulatory/consent** permission to influence suggestions, diagnostics, notifications, recipes, journals or decision-making. Neither `COMPUTE_SHADOW` nor `VIEW_RESTRICTED` implies this authority. The user-facing regular plan only uses eligible independently supported wellness actions.

**Critical boundary:** Shadow mode is not a regulatory loophole, medical-device exemption, waiver of privacy requirements, permission for hidden experimentation on real users or a backdoor into routine advice. Do NOT silently shadow-process personal genetics/microbiome/labs or send private data to Python/external services solely because a user has an account. Private Python service is still a distinct purpose/processor; default to internal synthetic/reference mode until correct purpose consent, approved sources/rights, encrypted resource/account isolation and no unauthorized external transfer are evidenced. Where an actual personal-data evaluation is not authorized, build, run and benchmark the same complete computation on synthetic/reference fixtures and replay harnesses, then mark `PERSONAL_SHADOW_DATA_NOT_AUTHORIZED` without stopping R&D.

## 3. Operational contract and noninterference
- For an **eligible opted-in/authorized test context**, run the shadow candidate using the same versioned validated input feature extraction, constraint set, eligible action pool, and model request pipeline as the ordinary baseline **when legally permissible**, then create separate unpromoted private candidate result and compare. For restricted R0-only models, use **equivalent synthetic inputs** with same code paths, clearly different data source; do not call synthetic replay a real-person prediction.
- The ordinary deterministic/approved model produces the public suggestion; experimental Python solver/model independently produces a shadow candidate. A shadow result **MUST NOT** change eligibility, ordering, food recommendations, nutrition totals, measured biomarkers, alerts, progress charts, ordinary API payloads, AI prompts, exported reports, push notifications, plan saves or any automated personalized behavior.
- Shadow outputs are stored if needed only as **isolated bounded encrypted internal audit/evaluation artifacts** with account-bound/purpose-bound access (or anonymized synthetic run ID), short explicit retention, version/source references, no raw report contents, no patient identifiers in logs and no user-visible cross-account references. Prefer aggregate evaluation metrics when feasible; never feed personal shadow outputs into training without separate consent/authorization. Cancellation, account deletion, source deletion/correction/permission revocation, model/evidence withdrawal invalidate cached pending and stored shadow outputs; handle queued jobs.
- Run asynchronously/out of the normal critical-path where safe (developer implementation job/queue, **not** a promise ChatGPT will do background work). Cap CPU/RAM/runtime/requests, isolate timeouts, rollback, circuit breaker; shadow failure never blocks meal logging, Today, active workout or baseline recommendation. Do not add paid infrastructure/compute without separate budget authority.
- Evaluation compares candidate against deterministic baseline with the **same** authorized inputs and exclusions, and records feasibility, excluded/unsafe recommendations (zero tolerated), source coverage, wrong-sign/uncertainty when measurable, latency/compute, drift, observed user task value if assessed with authorization. Unvalidated microbiome theoretical flux has a **different** benchmark from user action efficacy; it can still make research progress without a clinical PASS.

## 4. Privileged UI — faithful Bloom Branding
For an internally authorized account, after turning on **existing** `Show development features`, present a **clearly separated Experimental/Research view** reachable from existing Explore → Biology / relevant ML feature (not on default public Today and not a new top-level ML dashboard). The viewer exposes only server-permitted versioned results, source/assumption completeness, `Observed vs research vs simulated`, reference/synthetic/no-personal-data basis, model coverage/uncertainty and plain explanation. Include comparison against baseline as appropriate. Read-only `Inspect / Compare / Explain` controls, not `Apply` / `Recommend for me` / `Treat` / `Save to meal plan` for restricted models. For future personally authorized research output, explicit labelled scope and audit remain required.
The regular user sees the same supported ordinary wellness advice and no hidden layout, leaks, disabled menu placeholders, numerical model score, shadow result badge, or restricted source text. Avoid conflating an unmeasured qualitative taxon list with inferred actual gene abundance/SCFA concentration.
Toggle Off hides experimental navigation and revokes **viewer access** immediately in UI and server requests; does not erase properly retained separately authorized shadow evaluation history unless user revokes that purpose, but no restricted cache remains on normal client. Toggle expiration/role loss/revocation fails closed. Never require a second general toggle or direct public-access beta simply to complete internal ML engineering.
The Branding specialist's meaning-first hierarchy remains: research context upfront, assumptions and limitations within one interaction, original evidence accessible, 320/390px, zoom, keyboard, real model/server error states. Actual independent UX/Legal/Science/Security review is **final-gate/activation** not a coding stop-work permission.
