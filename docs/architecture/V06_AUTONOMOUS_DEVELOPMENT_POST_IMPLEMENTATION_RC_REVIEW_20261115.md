# Bloom — Autonomous Development, Post-Implementation Reviews, and One Integrated Release Gate
**2026-11-15 · Direct Product Owner decision · Governing development-process amendment · Effective immediately on `enhance/bloom-experience`**
**Owner intent:** Stop excessive intermediate approvals. Codex should implement the existing roadmap **without pre-development or per-feature specialist sign-off**; relevant specialists audit/review an integrated release candidate **after development and before merge into `main`**. Fix findings iteratively and present one coherent RC for owner review. **Do not interpret this as cancellation of protected runtime/privacy/clinical/rights safeguards.**

## 1. One simple development process
**Select next unfinished roadmap slice → implement fully → tests/source + privacy/authorization checks → commit/push to authorized development branch → verify running preview and record exact status → move to next slice → assemble integrated RC → parallel specialist audits + owner RC review → fix specific findings → merge/public release only when authorized.**

Codex owns day-to-day implementation choices, component/media production, migrations, research and development experiments, testing, integrations in non-production or permitted preview infrastructure, fixes and deployment to **authorized** development environment. **No owner, Architect, Biology, AI, Integrations, UX or Legal signature is required simply to begin, continue, complete or QA a roadmap implementation slice.** Do not create a "gate closure" workstream that holds up creating the actual product; don't send routine pending-approval requests. The owner proactively supplies corrections; silence is not approval of release, but it is not a development pause.

**A test failure is engineering work, not a committee decision.** Fix and retest. A real dependency (credential, actual source rights, provider entitlement, signed deployment, unavailable reviewer at final RC) must be named narrowly; use mock/synthetic fixtures or an authorized alternative where practical and continue other development rather than wait indefinitely.

## Shift-left specialist standards — efficient and secure development, without serial approval (owner clarification 2026-11-15)

**Codex must anticipate what specialist reviewers will examine while developing, rather than discovering obvious deficiencies at RC.** This is proactive engineering quality, **not** a pre-implementation signoff or requirement to ask agents to review every commit. Reuse the relevant existing specialist test expectations as checklists, not lengthy mandatory packets.

For each **selected slice**, write a compact risk/acceptance note **within the existing task or test receipt** (not a new governance file): `user task + expected outcome | touched data/security boundary | relevant 1–3 reviewer concerns | focused happy/negative tests | existing evidence reused | implementation vs exposure state`. Skip irrelevant domains; do not open all specialist handoffs for a minor CSS change.

- **Security/privacy (always for authenticated/user-data changes):** backend account/role authorization, tenant isolation, input and URL trust, safe secrets and logs, consent/purpose boundaries, denied-path tests, revocation/kill switches, reliable deletion and account switching. Never expose real health/genetic records or restricted unreviewed predictions to unauthorized users, services or environments. Unapproved outputs can be built using synthetic/test fixtures behind server controls.
- **Biology/scientific accuracy (when content touches health claims):** real measurement vs estimate vs interpretation, cited source/provenance/version/units/method, unknown ≠ zero, competing goals, allergies, conservatively worded noncausal effects, and no unsupported diagnosis, drug/dose, urgency or validated personalized prediction. Write focused positive/negative cases before publishing output for real-user execution.
- **Integration/data (when sources or persistence change):** idempotency, source identity, licensing and rate limits, timestamp/timezone, schema compatibility, retries/conflicts, unit/assay comparability, audit/revision history, provider outages and data corrections. Use actual existing test fixtures and source connectors.
- **AI/model (when applicable):** exact input/output contract, synthetic vs real, evidence trace, behavior on missing/contradictory source data, deterministic fallbacks, prompt/data privacy, reproducibility/version, model evaluation and safe degradation. Do not invent a new science engine.
- **UX/Brand/accessibility (when user-visible):** no lost original tasks/fields, information hierarchy and drill-in, consistent Everyday green/Athlete blue/Coach purple, contrast, mobile/desktop, keyboard, Dynamic Type/zoom, image fallback, honest experimental status and responsive performance.
- **Legal/rights (only where relevant):** asset/food/provider licences, lawful handling, actual territory/consent and accurate disclaimer/public claims. A licence violation is a real restriction on use, not a reason to stop writing independent code.

**Efficiency rules:** risk-tier changes `LOW` (styling/copy/ordinary local UI), `MEDIUM` (record persistence, source processing, diet/exercise guidance) or `HIGH` (sensitive data boundaries, consequential health conclusions, cross-account/research, external model/provider, production operations). Run proportional focused checks during each vertical slice; full multi-specialist sweep and broad regression **once at integrated RC**. If a high-risk issue can be prevented with a small change now, fix it immediately; if an external signature/rights is unavailable, keep that exact real-world exposure disabled and continue implementation/other safe work. Existing reviewer findings are **design input**, not compulsory per-step consultations.

**Outcome:** Codex ships better-tested features to the development branch faster and gives RC reviewers clean, bounded evidence. A reviewer can still find defects; those become precise RC fixes, **never grounds to restart already verified unrelated features**.



## 2. What may be built now vs. what may be enabled
- **Implement:** all existing frozen v0.6 Core and separately scheduled Advanced roadmap items, including behind-flag functionality, experimental/preview UI, source review, science models and private synthetic/reference computation. Native SwiftUI remains **late v0.6**, not pulled forward by the policy. New v0.7 feature ideas remain v0.7 unless owner expressly changes scope.
- **Development preview:** Codex can deploy tested ordinary low-risk functionality to authorized staging/review and offer appropriately labelled synthetic or educational previews for risky or unfinished capabilities, without obtaining new intermediate signatures. Maintain account/role controls, consent, storage isolation, feature kills, source provenance, rights and safe fallback. **Use synthetic non-patient data for clinical/research-model experimentation**; do not feed real sensitive health data to an unapproved service.
- **Do not silently expose:** clinical diagnosis, urgent-medical triage, treatment or dose recommendations; unvalidated personal genetics/microbiome predictions; unapproved secondary personal-data research/sharing; unlicensed datasets or charged provider execution; prohibited restricted API operations. Develop and verify these capabilities behind appropriate server-side exposure controls; relevant scientific, legal, privacy, provider and platform authorizations remain prerequisite to their *real-user execution or public release*, not to their implementation.
- **Public/production:** merge into `main`, App Store/public release, irreversible production migrations, paid services and new sensitive-data uses remain separately authorized. A feature can be fully developed while its outward exposure remains restricted.

## 3. Shift all routine specialist sign-offs to integrated RC
The previously described Biology Rev 2.0/2.1, ML 2201–2206, Integrations 01–05 and 14-capability gate-closure checklists become **development test specifications and eventual RC audit lenses**, **not serial prerequisites for Codex to implement or make safe development previews**. Their scientific/data-integrity constraints retain full force; no checks are erased. Review **in parallel** at integrated RC: Biology (scientific claims), AI (ranking/model behavior), Integrations (source fidelity and lifecycle), UX/Brand (usability, aesthetic and accessibility), Security (privacy/auth/isolation), Legal (rights/clinical jurisdiction), Architect (consolidated release scope). Reuse any existing valid prior receipts by same implementation/behavior; reviewers file precise defects/risks, not generic "not approved" holds. Codex implements corrections and targeted retests.

**Not every screen needs every reviewer.** Reviewer relevance is based on actual feature risk and implemented claims. Informational labels, usual food entry, plots of source values and cosmetic UX work do not require new ML/clinical opinions; medical and restricted personal-use claims require appropriate qualified review *before exposure*.

## 4. Explicit status distinctions and no-loop rules
Keep `NEXT_ACTIONS.md` as only execution queue, `AGENTS.md` as operating rules and `docs/operations/V06_DELIVERY_STATUS_LEDGER_20261115.md` as roadmap/done evidence, with existing `docs/verification/V06_CAPABILITY_GATE_CLOSURE_20261115.json` now an **optional evidence worksheet** for the 14 scopes, not a developer-blocking approval switch.

Use `ROADMAP / IN_PROGRESS / IMPLEMENTED_UNVERIFIED / ENGINEERING_TESTED / VERIFIED_ON_REVIEW_BRANCH / RC_REVIEW_PENDING / RC_FINDING_FIX / DONE_FOR_SCOPE` distinctly, plus `EXPOSURE_RESTRICTED` as a **separate field** (not "not implemented"). A capability with code/test evidence may be `VERIFIED_ON_REVIEW_BRANCH + EXPOSURE_RESTRICTED`, and Codex must continue the next task without waiting for a domain signature. Never change statuses based purely on a preliminary `CAPABILITY_EXPOSURE_MAP.json` source crosswalk, speculative reviewer concern or a dated old main SHA.

Before coding, locate current implementation and tests. If an accepted scope is already verified at applicable SHA, **do not redo it** without a new user correction or demonstrable defect. After two unsuccessful materially distinct attempts, record a precise blocker and continue another feature. Don't update multiple large handoffs after every commit.

## 5. Final RC entry, audit, signoff, release
Codex assembles a usable integrated release candidate with exact source/deploy ID, implemented capability matrix, enabled-vs-disabled scope, change log, test/CI receipts, rendered responsive UI/asset evidence, no-regression, account/consent/rights/source controls, known restrictions and unresolved P0/P1 risks. Domain reviewers do one **parallel post-implementation** risk review, logging only actionable defects/clarifications and any genuinely independent authorizations required for release. Owner evaluates imagery, UI and functionality together and gives corrections. Codex closes findings, republishes the RC, and records actual approvals. **Do not invent or pre-fill final signatures.** Merge to `main` or public production only after actual authorized approval and required safety/rights compliance.

The freeze of v0.6 **scope** remains, but this document supersedes any older claim that specialist pre-signoff must occur before a feature can be developed, built, unit-tested, safely previewed or marked engineering-complete. All corresponding historical detailed review checklists remain available as RC test/acceptance evidence, never discarded.

**Controlling priority:** BUILD FIRST → VERIFY → REVIEW TOGETHER AT RC → CORRECT → RELEASE WITH APPROVAL. No interim feature approval treadmill.
