# Bloom — v0.6 Requirements Freeze and v0.7 Intake Policy
**Date:** 2026-11-14 | **Status:** Owner-authorized requirements baseline freeze; implementation ongoing. 
**Authority:** Owner: “We can likely freeze v.6 with these requirements and anything new go into v.7 unless it’s necessary to be in v.6.”
**Purpose:** Prevent continual feature expansion while Codex finishes the genuinely useful v0.6 Core and permitted dependency-scoped Advanced work.

## 1. Frozen v0.6 baseline, not a development stop
The v0.6 requirements baseline comprises all **approved and controlling** owner directives and reconciled architect decisions as of 2026-11-14 under `docs/architecture/V06_HANDOFF.md`, `docs/architecture/V06_CORE_ADVANCED_EXECUTION_CLASSIFICATION_20261114.md`, `docs/operations/V06_DEPENDENCY_BACKLOG.md`, and the already-approved specialist/owner handoffs referenced by `NEXT_ACTIONS.md`. **No previously approved requirement is silently deleted.** The approved split is:
- **Core** — practical Today, authentic Food→sourced editable dinner and consumption confirmation, full-report bloodwork Response Intelligence, source-accurate macro/micronutrients with safe references and supplement context, reliable USDA/CNF 2026/Canadian DRI/LOINC/UCUM pilot integrations and coverage receipts, Adaptive Health Guidance with protected goals/observational learning, activity and Progress basics, account/privacy safeguards, optional initial future-research-contact interest **not** data sharing, accessible editorial UX, actual end-to-end test evidence.
- **Advanced** — previously authorized molecular reference modelling and private Python research, scientific AI literature review/contradiction and model registry, advanced response inference, sophisticated Athlete and Coach functionality and future source/provider features, **as their independent data, rights, privacy, safety, regulatory and validation dependencies are satisfied**. Scope remains recorded; Advanced does **not** automatically gate Core availability. Future external cross-user research/pooling and clinical uses stay separately unauthorized.
- **Shared safety/foundations** — account boundaries, consent, source provenance/corrections, rights, reproducible scientific eligibility, safe error/unknown states, hard contraindications and testing apply to both.

**Freezing requirements does not freeze defect fixing, data acquisition/refresh, scientific review, tests, integration, UX corrections needed to make accepted functions usable, or implementation details.** Only scope expands by exception below. Existing Advanced work continues where it doesn't displace Core; a release name is not proof a capability is ready.

## 2. New request classification and decision policy
For every **new** proposal arriving after this freeze, Codex and Architect should first check whether its substance is already part of an accepted v0.6 requirement. Do not treat specification clarification or acceptance proof as a new feature.
1. **Existing v0.6 implementation/clarification:** Required to realize a frozen feature, preserve agreed user benefit, resolve ambiguity, meet already-set acceptance tests, or complete an approved independent Advanced slice. Do in v0.6 under the relevant existing work item. Record a short rationale and linked source; no owner gate.
2. **v0.6 necessary exception:** A reproducible serious defect, privacy/security vulnerability, consent violation, source/data/units/science inaccuracy, material clinical/safety issue, regulatory/rights requirement affecting v0.6 release, or **essential missing functionality without which a Core promised end-to-end journey cannot be achieved**. Include in v0.6 with reason, affected requirement, least-scoped fix and tests. Architect resolves scope ambiguities and documents the exception; **no new intermediate owner signoff** for routine corrections, while applicable external clinical/legal/regulatory authorization still governs consequential activation.
3. **v0.7 candidate (default):** New dashboards, integrations, models, visual concepts, niche use cases, research extensions, optional analytics, major workflow changes, additional provider families, and enhancements not necessary to meet frozen v0.6 acceptance. Capture in a **lightweight v0.7 intake section** with benefit, dependency, privacy/science implications and proposed priority; do **not** implement in v0.6 merely because it is attractive.
4. **Explicit later owner override:** The owner can deliberately reprioritize a candidate into v0.6; document precise scope/impact. An override doesn't waive consent, legal rights, safety or independently necessary clinical review.

**No fake freeze exceptions:** Future research contact preference does not enable actual research use; a source API returning data doesn't mean source/science clearance; an experimental model can't bypass personal output gates; repeated developer curiosity about a model isn't Core necessity.

## 3. Codex process — one active queue
- On each next task, inspect latest HEAD and existing issues before making changes. Use `NEXT_ACTIONS.md` as the sole active engineering order, `docs/operations/V06_DEPENDENCY_BACKLOG.md` for evidence/dependencies and the Core/Advanced classification for priority. Do not create a parallel sprint plan/roadmap or request repeated owner decisions.
- Label new intake in the existing queue or issue as `v0.6-existing`, `v0.6-exception`, or `v0.7-candidate`. For exceptions, document objective impact and minimum acceptance check; for v0.7 capture only a brief candidate entry.
- **Prioritize** real app Food #12 and full-panel Response #15 with supporting real source acquisition and safety; then remaining Core user journeys, source coverage, release verification. Advanced synthetic/reference/scientific jobs can proceed under bounded parallel capacity with their own documented gates.
- Do not shift v0.6 release target because an optional Advanced model/source is unresolved; carry that capability under its same approved but not-yet-eligible status or reconsider **delivery timing** independently without pretending it was implemented.
- Maintain transparent statuses: frozen requirement vs code implemented vs scientific/source rights validated vs app tested vs hosted vs human validated. Freeze date is NOT approval to ship or a declaration of completion.

## 4. Quality and regression acceptance
- v0.6 Core must produce actual sourced safe daily guidance, specific Food actions, broad lab insights, practical nutrition, protected-goal adaptive response and functioning account/source workflows through authentic API/database/browser journeys, with exact SHA and honestly identified external-science/rights gaps.
- Security and privacy defects, harmful clinical outputs and incorrect source data remain valid in-version exceptions regardless of freeze.
- Evaluated user research/test insights may generate **v0.6 fixes** only when they show failure to meet an existing acceptance or serious safety/usability deficiency; optional enhancements default to v0.7.
- Continue preserving research-ready Canada/US (EU future) information, scientific AI risk gates and day-one contact preference as already approved; no new general-user research UI or collective data use.
