## Binding implementation

### A. One walking log with estimates and editable measured facts
- Show in first-level quick-log (not hidden under unrelated disclosure): `Steps completed` (confirmed integer or blank), `Duration` (reported minutes or blank + clearly shown estimate when possible), `Estimated exercise energy` (kcal and coverage/method), `Effort` if available; retain optional distance. Time correction must be easy (`2 hours` -> 120 min).
- **Do not auto-save guessed duration as recorded actual.** Estimate from per-user comparable actual step/minute sessions (minimum evidence, sufficient sample, sensible outlier checks) or a **disclosed generic cadence range** rather than a made-up personalized walking speed. Show `Estimate ~X–Y minutes, based on assumed cadence`; user can accept into *estimated* field or override with actual entry. No step-derived distance unless a separately validated stride/measurement exists.
- **Exercise calories are uncertain model outputs**, not automatically measured. Prefer source-specified reported workout energy if present, but label provider estimates as estimates too; otherwise bounded MET/intensity/duration/body-mass method where applicable, with exact method/source, known equipment limitations and confidence/coverage. Do not claim a numerical value where key inputs absent; never treat whole-day steps as one extra 2h walking session without confirmed episode. Allow user correction/override and preservation of original estimate, revised value and user reason/source in immutable revision, not destructive replacement.
- Explicitly distinguish **gross vs net activity energy** (net calories *above resting expenditure* for active add-on); no assumption that all workout calories should be eaten back. Avoid double counting energy in baseline activity factor, whole-day device activity, walking-pad steps, Peloton session and overlapping Watch workout. If cannot disambiguate, abstain or show uncovered range with overlap warning.
- Use `source session / whole-day`, actual vs estimated, interval and original units, owner, effective date/time, import/source version and audit, optional intensity. For current schema a minimal additive typed observation/derived estimate contract may be used, never a duplicate activity table. Existing training sessions, routines, Activity history, Progress and Athlete must read same updated canonical record. Known unknown stays null.

### B. Daily energy balance as useful but probabilistic feedback
- Expose **recorded intake vs estimated expenditure** separately; if enough valid profile + mass and actual food/activity, compute *bounded* expenditure estimate (resting energy + non-exercise activity + exercise + thermic effect as appropriately defined), while explaining source assumptions and uncertainty and avoiding double count. Need independent quality/coverage gating; if meals missing, do not infer full-day intake or a real deficit. `Under logged intake` is not necessarily a `calorie deficit`.
- User must be able to inspect/adjust baseline activity context and exercise source estimates without covertly overwriting the underlying recorded events. If reported wearable energy is total/day, treat it as an alternative total source, not additive session energy.
- Show neutral meaningful states: `Recorded 1,850 kcal; day incomplete, balance unavailable` / `Based on complete recorded day and your selected activity assumptions, estimated ~X kcal below/above expenditure, substantial uncertainty` / `Insufficient data`. No deterministic forecast of weight change from one day; evaluate **multiweek weight trends** against average intake/expenditure and changes (fluid/glycogen and metabolic adaptation caveats); no personal clinical treatment/diet targets or automatic caloric compensation prescription. Derive user-facing actionable meal guidance within reasonable goals, preferences, food availability and upper limits, not “eat back every exercise calorie.”
- Differentiate planned vs performed activity, estimated vs reported energy, ingestion unknown vs zero, consumed supplement vs scheduled. Correction/deletion/invalidation must refresh summaries, Food/Today/Progress/Athlete and cached proposals, preserving original history.

### C. Fix servings and other controlled-number editing
- Implement editing input **draft text state**, with empty allowed while focused; validate on blur/save/commit (positive finite servings, suitable bounds and decimal handling); selection/focus should support replacing entire 0/1 with a new value. Clearing must not force `Number('')===0` immediately. Preserve valid previous canonical quantity while draft is incomplete; show clear inline error; never commit 0 or NaN as consumed positive servings.
- Audit adjacent Food quantity fields, saved-meal portions and household quantities for the same zero/leading zero bug; reset draft correctly on product identity change, cancel, error and async recalculation; avoid cursor jumps, accidental mass scaling during intermediate edit or duplicate nutrient calculations. Test 0.5, 1.25, 2, paste, delete, focus/blur, touch keyboard, mobile decimal separators as supported, update original grams and label basis precisely, partial/unknown composition retained.

### D. Today must recommend actual specific feasible action
- Replace `One good next step` empty generic default with source-grounded **concrete** options: e.g. a **specific meal/food plus portion** drawn from verified items/preferences/goal and remaining coverage; or a **specific practical exercise** (duration/modality/effort) from actual feasible routine, equipment, goals and recovery/safety constraints; or recovery/sleep where appropriate. State what, why now, estimated effort and evidence level. Example copy may use synthetic fixture meals only; never hardcode same meal for every user.
- Reuse approved meal planner/product search, existing action library, goal-aware food exclusions/allergies, saved routines and action ledger; `Try` opens a **prepopulated editable** Food composer or activity/routine planner, not merely an opaque button or a generic logs page. `Not for me` with reason/alternative; user decision is not automatically performed/eaten. Missing logged data shouldn't make all general advice disappear.
- User-facing transparent **one primary action**, optional alternate `Eat / Move / Recover` access, no repetitive generic journal instruction as hero if meaningful action can be offered. When no safe concrete suggestion, clear abstention with practical general alternative, not invented biological score or fake nutrition gap. Validation must demonstrate that dietary options really change with exclusions, goals, time of day, source coverage and recent activity; do not overfit walking-pad user.
