## 2. Five-step engineering algorithm applied to information architecture
**Step 1 — Question:** For each prominent screen element, identify the actual user question/decision and evidence source. Ask: Does this help understand, decide, act, verify or navigate? If not, is it a necessary trust/consent/safety control? Remove status decoration when it has no meaning. Don't question away required consent, lab source, drug safety or app capability.
**Step 2 — Delete unnecessary presentation, NOT information:** Remove duplicate headings, redundant micro-cards, repeated badges, near-identical CTAs, vacuous scores and visual scaffolding. **Move valuable secondary details into accessible expanded panels or linked detail views**, with status+source+unit still recoverable. Do **not** delete raw lab rows, nutrient fields, genetics observations, reported microbiome entries, data provenance, actionable alternatives, data corrections, protected-goal tradeoffs, settings or user tasks.
**Step 3 — Simplify then optimize:** Give each screen a focal question, a primary action and up to ~3 meaningful secondary actions (not a rigid cap hiding needed safety). Use a clear hierarchy: editorial summary → what changed / why it matters → next action → expandable source, limitations, science. Prioritize readable labels, useful whitespace, editable existing workflows and compact cards. Use *appropriate density*: Today/Food warmer and scannable, Biology/Explore richer visual atlas with expandable research, Progress precise readable longitudinal ledger, complex reports deep but uncluttered. Navigation stays predictable; avoid endless nested accordions, critical data hidden behind mystery icons or excessive taps.
**Step 4 — Accelerate:** Optimize common food/activity capture, search, review, logging, Lab/Progress retrieval and primary transitions, with actual latency measurement and perceived performance/skeletons; keep safe loading/error states and interaction feedback. Fast means easy and responsive, **not** skipping source reviews, confirmation, accessibility or backend permissions.
**Step 5 — Automate last:** Automate repeat-safe formatting, source-bound summaries, personalized prioritization and defaults after user behavior is stable and tests pass; never silently log meals eaten, choose medication doses, change data/consent, auto-promote research, or hide errors. Automation must be inspectable, undoable when feasible, and unavailable without required evidence/permissions.
**Measure:** first useful action comprehensibility, key-task success, time/taps to core task, number of competing high-emphasis elements, data discoverability, source provenance comprehension, error recovery, accessibility and zero lost capabilities. Do not chase an arbitrary “minimum cards” metric if it erases meaningful data.

## 3. Aesthetic tokens and component language
Inherit Stitch hybrid tokens and art direction (`#faf9f7`, `#012d1d`, `#1b4332`, `#3f6653`, `#d1e4de`, `#dd9832`; editorial Newsreader + readable Plus Jakarta Sans; paper/ceramic shallow surfaces, inset control, delicate scientific rules, deep botanical anchors). Codex shall:
- Own **one semantic token/typography/spacing/shape/motion/visualization system**, with light and dark equivalents, and accessible states; migrate old components gradually with explicit parity coverage. No route-specific conflicting green/gold palettes, giant dashboard KPI defaults or generic SaaS bordered-stack regression.
- Create/refine reusable **patterns**: quiet header and navigation; editorial hero; understated action focus; beautiful food image/meal history; metric and source label; compact timeline and trend chart; scientific atlas nodes; micro-legends; paper ledger/table; modal/drawer/expanded evidence; form/validation; empty and error state.
- Use visually distinctive illustrations/icons intentionally and consistently, not decorative icon scatter. Fonts/images must be legally usable, local/first-party or approved assets, robust to missing remote resources.
- Preserve functional contrast, native browser zoom, text scaling and reduced motion. Avoid 9px system text except decorative nonessential labels; all important labels readable with zoom. Desktop and tablet must be genuinely composed, not a mobile mock stretched to wide screens.
- Match density to user need: simple daily summaries default; **drill-in as a first-class polished experience**, not a dumped raw table. Expanded states have breadcrumb/back, context, sources, unit/method and appropriate action. Keep original record/export access where authorized.
- **Scientific data stays scientifically honest**, but placeholder mock numbers are NOT the focus of design critique; science integrity remains existing runtime policy and a release-blocking defect when fabricated.

## 4. No-regression invariant — before any component deletion or navigation revision
**Functional preservation ledger for EVERY route:**
`route | role/experience | current feature actions | current data sources | loading/empty/partial | create/edit/save/delete/export paths | old navigation access | new summary placement | new detail access | tests | screenshot | status`.
Codex must first check actual App.tsx/BottomNav/AppNavigation/AppHeader and active route definitions. Current code suggests **mobile BottomNav selects only Today/My Biology/Progress while desktop navigation has separate ‘More tools’ Food, Activity, Meal plans, Explore, Gut reports etc.** Do not assume the Stitch 5-tab mock reflects current production navigation or remove the legacy paths. Propose a coherent five-destination primary shell while preserving every active secondary route via obvious in-page links, drawer/menu and correct back state; actual mobile reachability must be tested without URL typing. Athlete mode must preserve its full workspace and role-gated features.
**Baseline screenshots AND feature tests before edits** for at least Core Food/Today/Biology/Explore/Progress and deeper Food Review, Lab Reports, Activity, Athlete, Profile, import/upload, sign-in. Account isolation and consent checks are nonnegotiable. Compare before/after on same representative synthetic fixtures; no false “app parity achieved” if old interactions never audited.
- Food: actual vs planned, ingredient/portion review, source/unknown, authenticated save/edit/reload, manual food and supplements.
- Lab/Progress: all original report rows, dates, source ranges, unit and assay comparability, history revisions and original export; non-TG markers remain findable.
- Biology/Explore: known observations and source links separate from studied/predicted research; source-gated deep views and super-user authorizations unchanged.
- Activity/Athlete: actual workout/event history, review/edit, manual fallback, features/settings across role transitions.
- Privacy/settings: consent, deleting source, account switching, role expiry and research-interest preference still work when eligible.
- Every important interactive CTA has working route/action; no `href=#`, dead prepare/log buttons or silent incorrect success states.

## 5. Detailed delivery sequence without a new planning cycle
1. **Audit:** latest HEAD, current routes/controls and design branches, existing Brand original package and Stitch 10-screen ZIP. Create route/feature preservation ledger as part of implementation PR (no separate project).
2. **System-first:** implement global tokens, typography, icon/illustration rules, nav/header, surface components; assess new shared defaults against every page before merging.
3. **Flagship proof:** Today and Food together with real persisted user interaction, then Biology/Explore/Progress; capture at 320/390/768/1440px light/dark/zoom, with responsive states and browser screenshots.
4. **Full-app cascade:** extend the **same** system through all deep pages, settings, Athlete, forms, dialogs and error states. Fix visual inconsistencies/hidden actions while preserving all data and flows. This is a required step before visually signing off the owner request.
5. **Parity and polish:** route diff/checklist with explicit no regression, focus/keyboard/VoiceOver, contrast, safe areas, reduced motion, persisted records, API/DB, two-account privacy, source/claim filters, CI, exact Render SHA, representative task testing. If a page can't migrate safely, keep functional existing version accessible and mark partial theme adoption honestly; don't break it to claim 100% visual coverage.
6. **Resume frozen v0.6 priorities** (Core user value and scoped independent Advanced) after this owner-priority comprehensive theme integration and substantive regression pass, except emergency security/safety/source fixes.

## 6. Acceptance / objective sign-off
- **Coverage:** 100% of **active, reachable, authorized routes** inventoried; 100% of their existing critical actions either preserved and demonstrably tested or explicitly documented as a pre-existing failure/blocker. Theme application to all audited public Core and Athlete surfaces, with no unexplained legacy appearance. Role-gated development features remain role-gated.

- **Interaction:** real food log/edit/reload, lab full panel, activity save/correct, profile/consent and navigation from every primary destination and deep-screen return verified. No dead CTA, duplicate save, permission bleed-through, broken drafts or modal traps.
- **Appearance:** unified warm botanical editorial identity, differentiated page rhythm, polished charts and depth, consistent in dark mode, all supported breakpoints and empty/error states. Expert design assessment not inferred from passing unit tests.
- **Evidence:** actual screenshots and status receipts at same HEAD, CI, authenticated app/API/DB, hosted Render and independently tested UX as `PASS/FAIL/NOT TESTED` individually; don't equate mockups or implementation with validation.
