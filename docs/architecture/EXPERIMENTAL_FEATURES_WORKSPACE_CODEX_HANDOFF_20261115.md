## 3. Server-driven catalogue contract — reuse existing architecture
Extend **existing** `GET /api/capabilities` and the `shared/development-features.ts` presentation type (or a narrowly scoped existing manifest projection) with a display-safe typed array:
```ts
type ExperimentalPresentationEntry = {
  id: string;                    // actual stable approved capability ID
  group: "AI_FOOD"|"ATHLETE"|"BIOLOGY"|"GENETICS"|"COACH"|"INTEGRATIONS"|"RESEARCH";
  title: string; description: string;
  readiness: "PLANNED"|"IN_DEVELOPMENT"|"TESTABLE"|"FUNCTIONALLY_COMPLETE"|"VERIFIED"; 
  visibilityStatus: "AVAILABLE_FOR_TESTING"|"DEVELOPMENT_PREVIEW"|"IN_DEVELOPMENT"|"PLANNED"|"RESTRICTED";
  interaction: "OPEN_APPROVED_ROUTE"|"OPEN_SYNTHETIC_PREVIEW"|"INFO_ONLY";
  route?: string;                // strictly server allowlisted known in-app destination; never arbitrary URL
  sourceClass?: "SYNTHETIC_ONLY"|"EDUCATIONAL"|"ACTUAL_AUTHORIZED";
  limitations?: string[];        // sanitised, short; no private evidence or secrets
  prerequisites?: string[];      // only appropriate permitted metadata
};
```
Schema is illustrative; Codex should reuse actual capability IDs, schema validators and UI statuses rather than creating second entitlements or a parallel source of truth. Internal server **display projection** may maintain small versioned mappings for user-facing title/category/description and **verified existing route/preview**; existing Legal provisional registry is a classification INPUT, not proof of installed route or permission. Link actual availability to current server-authoritative effective-decision, existing verified implementation/feature activation, environment, grant scope, territory, role, purpose, consent, expiry, kill switches, and account preference. **A working UI route alone is not sufficient.**
**Important distinction:** A tester may have permission to view sanitised PLANNED or IN_DEVELOPMENT metadata without permission to execute a feature. Model two independent server-filtered properties **metadataVisible** and **actionAllowed**; do not accidentally demand full model execution authorization just to show safe public development status, and do not let display visibility confer action permission. For `RESTRICTED`, only metadata specifically permitted for this account; restricted science/research details and clinical models stay hidden or redacted where needed. Unknown IDs, inconsistent state, denied grant, unverified route, missing permission or ambiguous environment → fail closed (hide restricted metadata or show no-action generic status, depending on approved disclosure).
**Do not hardcode the four examples as approved working capabilities.** When no eligible authorizable entries exist, show a graceful empty informational notice, not feature buttons; explicitly maintain the currently working `bloom.food.photo_ai` synthetic file experience and exact existing permission envelope. No generic `/api/experimental/:id/run` or broad grant mutation.
**Security**: `GET /api/capabilities` continues auth/`no-store`, eligibility/grant fingerprint validation and session/account scope. Extend `internalPreviewGrant` only as needed to read **explicit permitted capability IDs**, not to broadly relax `uiPreview` grant schema or automatically populate the 52 Legal entries. Distinguish UI-preview grant from any model/service execution grant. Keep server checks at each route/API/AI tool/export/background job; disallow attacker-crafted route/URL values.
**Revocation**: OFF toggles server preference, client immediately hides entries, cancels/evicts restricted queries, closes/restricts previews where feasible, clears local synthetic object URLs, and honors account switch/grant expiry/revocation. Existing `useCapabilities` anti-stale handling must be preserved, extended only to actual new restricted cache keys. Stale server permissions must be rechecked at action time.
**Read-only admin**: `/api/admin/features` remains separate with role/scope/metadata and no execution. No loading its entire 52 entry Legal view as user content.

## 4. Status mapping and truth table
| Server verified fact | UI label | Entry action |
|---|---|---|
| Action permitted + actual tested route/feature functionality and approved tester scope | **Available for testing** | Open actual approved route; backend still authorizes operation |
| Explicit synthetic-only UI preview with server test scope; not actual AI inference | **Development preview** | Open preview, clear synthetic disclaimer, no personal scientific analysis |
| Implementation begun, no functional authorized preview | **In development** | Informational only |
| Approved roadmap concept, no usable implementation | **Planned** | Informational only |
| Metadata allowed, execution requires independent science/privacy/legal/clinical grant | **Restricted** | Informational only, no route/model invocation |
| Incident kill switch/withdrawn | **Disabled** | Hidden from ordinary workspace, accessible only to separately authorized admin metadata |
| Unknown, ambiguous, or expired grant; forbidden category | **Not disclosed** | No entry; fallback/normal app unaffected |

**Implementation readiness** (`PLANNED/IN_DEVELOPMENT/TESTABLE/FUNCTIONALLY_COMPLETE/VERIFIED`) is NOT **tester execution authorization** and NOT **public release approval**. A provisional Legal `GENERAL_RELEASE` entry can still be unavailable; `HIDDEN_PENDING_APPROVAL` can still be metadata-only. Ensure no false claim of deploy success or completed scientific validation.
