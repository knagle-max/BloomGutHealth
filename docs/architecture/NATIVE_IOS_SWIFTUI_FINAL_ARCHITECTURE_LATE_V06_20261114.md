## 1. Final decision and precedence
The owner explicitly selects **fully native Swift + SwiftUI from the first iOS commit**, replacing the earlier **Capacitor-hosted React companion** in `docs/architecture/V06_HANDOFF.md` §35. **No Capacitor spike/app, React Native, embedded WebView primary UI, interim hybrid release or throwaway native prototype.** UIKit may be used selectively for an actual unsupported SwiftUI requirement. Use Swift Charts, Swift Concurrency, URLSession, Keychain, HealthKit, supported BackgroundTasks/HealthKit observer delivery and native Apple accessibility/appearance as appropriate; watchOS, WidgetKit, Live Activities and optional Apple framework use remain **dependency-/feature-approved** rather than automatically delivered.

**Timing is equally binding:** this is **one of the last planned v0.6 development workstreams**. Codex's current priority remains (1) genuine security/privacy/science correctness incidents, (2) owner's app-wide immersive design, visual asset registry/generation, route and no-regression work, (3) v0.6 Core Today/Food, whole-panel bloodwork, nutrient/source integrations, adaptive guidance, activity, QA, then other already-approved independent Advanced slices as dependencies permit. **Do not interrupt these for a speculative SwiftUI build, sign-in spike or entitlement provisioning.** Nonblocking API/authorization contract compatibility and future app metadata may be documented during web development when already needed; native implementation starts late in v0.6 at a documented dependency point. **This changes the implementation architecture, not the frozen consumer feature scope.** Do not confuse native code completion with web v0.6 Core release readiness, or force a partially implemented app into App Store merely to meet a version date. Native release has its own full acceptance gate.

## 4. Permanent native codebase architecture
**SwiftUI modules/features:** AppShell + ModeTheme (Everyday evergreen / Athlete authentic blue / Coach authentic purple, native presentation), DesignTokens/Components, Auth/Account, APIClient, SourceStore/ProvenancePresentation, Today, Food, Biology/Reports, Explore, Progress, Athlete, Connectors/HealthKit, Privacy/Settings, eventual Coach with guarded role permissions, AssetCatalog. Use a deliberate module layout only as justified, don't force architectural micro-package sprawl.
**API contract:** versioned, documented OpenAPI/schema where beneficial; generated Swift DTOs only if generation quality checked, never separate client-only scientific truth. Reuse existing server endpoints first; add minimal capability-specific endpoints only when actual SwiftUI journey requires it. Preserve source revisions and historical method/unit/unknown; avoid auto-converting missing to zero.
**Offline:** account-scoped encrypted-at-rest-as-supported protected cached read content and queued commands only for safe user edits; explicit pending vs server accepted states; secure delete on account switch/logout; idempotency keys and revision/conflict responses; no silent reordering of clinician/scientific records. HealthKit anchor checkpoint advances only after reliable local+server reconciliation; failed uploads/revocations cannot result in silently omitted data.
**Apple data policy:** HealthKit permission is only device-data access, not research participation, Coach access, AI training, external data sales or wholesale secondary processing. Respect the independent early future-research-contact **interest** preference and separate actual study-specific authorizations (not activated).
**Image/design:** use approved first-party AI visual library and permanent BVA visual asset IDs, native-rendered image variants and SwiftUI counterpart designs; preserve quality level of owner Bloodwork screenshot, fast offline fallbacks and source-safe conceptual labels. No second visual registry.
**Framework caution:** BackgroundTasks and HealthKit observer updates are best-effort OS-managed, not continuous runtime. Apple documents HealthKit anchored queries and observer background delivery as separate mechanisms. Source: https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery , https://developer.apple.com/documentation/healthkit/reading-data-from-healthkit , https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.healthkit.background-delivery .
