## A. Owner override and data minimization ruling — controlling requirement

**PDF-FIRST.** The product owner explicitly requires directly uploading the Viome PDF in its native structure, automatically extracting usable report data with an accurate preview and correction workflow, then saving reviewed findings. A JSON export is a secondary optional input using the same canonical parser/result contract and consent; **never force conversion of PDF to JSON or manual copy/paste**. The requirement is an end-to-end upload→extract→review→save→browse workflow, not an illustrative file-picker that fails at review.

**NO PII INGESTED INTO STORED RESULTS.** The owner explicitly prohibits grabbing/storing personally identifying fields from PDF: **name, DOB, client/patient ID and analogous identifiers**. This supersedes Biology's earlier suggestion to preserve confidential identifiers, raw PDF attachments, provider test/sample/kit IDs in protected metadata. It also supersedes the companion handoff's proposal to link reports by retained test/sample IDs. Those instructions are no longer valid for this product path.

**Allowed biological/report metadata only:** provider/test **type**, specimen **type** (e.g. fecal), collection/received/report dates when present, qualitative RNA methodology and limits, original *organism names*, bacterial/viral/eukaryotic classifications, provider-specific categorical score/food text when relevant, page/column references only to the **de-identified interpretation fixture**. Dates are permitted because they are needed for longitudinal biology, but they must not include DOB or patient's biographical dates. Internally generated random record IDs are allowed. No provider sample ID or test ID, even in “private” metadata, original filename, search index or export.

**Never persist or forward:** original unredacted PDF, screenshots/page images containing identity, original PDF metadata or XMP, full extracted text, DOB, name, provider order/customer/client/sample/test/kit identifier, account-linked report identifiers, address/telephone/email, signatures, barcode/QR content, membership fields, hidden PDF text layers, filename-derived identity, PDF checksum/fingerprint of *raw original bytes*, or raw text chunks in error payloads, job queue, blob stores, caching, analytics, telemetry, logs, crash reports, tracing, observability, background OCR queues, external AI/LLM/research API or exported bundles. Personal account ownership remains server-scoped through existing authenticated Bloom user ID; this is not permission to use PII parsed from the PDF as a join key.

**Processing exception for mechanics, not retention:** PDF bytes will necessarily be transiently read to extract biological data; this does **not** authorize extraction of PII into business fields. Use a bounded short-lived authenticated processing context (prefer volatile memory; no disk/spool by default) with upload body/logging disabled, no persistent original file or temp file, no external processor call, no user-identifying filename/path, no general text search/OCR index. Parse only allowlisted Viome sections, immediately discard page-level content after sanitized record extraction, overwrite/expire processing buffers as feasible, and clean on cancellation/error/timeout. A strict memory-clearing guarantee in managed runtimes is not realistic; require **no deliberate persistence/forwarding and narrowly bounded lifecycle**. If the deployed framework, proxy, PDF reader or OCR cannot meet this, fail closed and make the blocker explicit rather than quietly persisting raw PDFs.

**De-identified preview and review:** The UI may display source-organism labels, provider category/score/food rows, matching source page number and report dates. It may **not** offer “View original unredacted PDF” from server storage. For source verification, while the user's local file is still selected, allow browser-local original preview without upload persistence **only if** product privacy review accepts it; otherwise use a sanitized reconstructed page/row preview without header/footer and a “Select the original PDF again to inspect” option. Never store full page excerpt or highlight text if it might contain identifying headers/footers. Export only curated, deidentified findings and general methodology—not a disguised raw document.

**Safe dedup and paired report linking:** One user-owned internally random specimen/report event, separate document-kind source records and deidentified normalized findings. Idempotency keys may derive from *allowlisted semantic content* plus provider/date/document kind using a secret-keyed account-scoped digest; do **not** persist a raw PDF SHA (may act as a stable fingerprint of identifying bytes). Companion PDF linking may use owner-selected existing report plus compatible collection date/specimen/method, user confirmation and validated content, **not** provider test/sample IDs (even transiently used as retained linkage). When ambiguous, keep two unlinked entries and ask user to choose; never silently cross-link based on date alone or combine across accounts.

**Privacy policy and review status:** This is an architectural privacy preference, not a claim that existing code has already implemented it. Security must audit actual request infrastructure, file parser, persistence, error telemetry, backup/cache and browser flows before treating PII-exclusion as achieved. Existing older historical imports holding original PDFs/identifiers require separate privacy inventory and user-directed remediation/deletion policy; no covert silent destruction of user data.

## C. Mandatory P0 privacy and parser acceptance suite

1. **Source fixture 7-page PDF:** 94 entries exactly (82/7/5), wrapped `B. thetaiotaomicron VPI-5482`, `F. prausnitzii A2-165`, `B. fragilis 638R`/YCH46 and source pages; no `0%`, no abundance values or functional scores; proper collection/received/report dates.
2. **Source fixture 13-page PDF:** 22 qualitative provider classifications, 299 food categories (240/28/22/9), correct tricky label and column positions, no score percentages; preserve provider attribution but do not impose `Avoid` as allergy; no automatic fish suggestions overriding user's dietary preferences.
3. **PII canary tests on both PDF fixtures:** inject distinct made-up name, DOB, client ID, test ID, sample ID, order ID, contact address/email/phone, MRN/barcode text, PDF author metadata/XMP, embedded filename plus repeated headers/footers and invisible text layer. Run PDF upload→extract→preview→save→reload→export/delete and assert **none** of those canary strings or original PDF bytes/identifiers occur in persistent database/object storage/backups created by the feature, logs/telemetry/traces/job records, URL/path/header, external API calls, cache or downloadable artifacts. Distinguish permitted report collection dates from DOB. Test error, cancel, interrupted upload, timeout, missing parser dependency, corrupted PDF, and unsupported scan paths. Raw provider identifier must not be used as saved dedup key. Inspect actual deployed HTTP pipeline, including reverse proxy/multipart spooling and cloud SDK telemetry, with sanitized test fixtures.
4. **Negative saved-schema tests:** field fuzzer tries to inject `clientName`, `birthDate`, `patientId`, `testId`, `sampleId`, `filename`, `rawPdf`, `rawText`, `fullPageText`, `originalFileSha`, and unexpected metadata/JSON fields; all rejected or discarded and never round-trip. A source page index may survive; a raw page excerpt with identifiers may not.
5. **Cross-account/dedup:** two users upload byte-identical synthetic reports with different synthetic identifying headers; neither user's internal record, source event or dedup match leaks to the other. Same user reuploads with differing header ID but identical biological content: no duplicate biological rows when owner confirms appropriate same report; different dated results are separate events.
6. **Ambiguous pairing:** recommendations PDF uploaded first then organism PDF, mismatched collection dates, repeated same-date samples, no specimen identity known. Never auto-merge on date alone or save test IDs; require user choice for uncertain linking and preserve independent documents.
7. **Quality failures:** three-column wrapped text, hyphenated labels, missing/partial column, PDF heading in different placement, duplicated headers, scanned/textless files, encrypted documents, wrong provider format, malformed structured report and JSON optional. Show page/field-specific errors without including PII in error details; no false '94 successful' on partial extraction.
8. **Nonregression:** quantitative microbiome history stays quantitative when truly measured, qualitative Viome remains `reported` with null abundance, source revisions and versioned taxonomy/food mapping preserved; compare counts only with method caveats; no personal BFT/toxin, butyrate, species-relative-abundance or functional-rate prediction.
9. **Real UX:** 320px/200% zoom, phone/keyboard/VoiceOver, two documents and mixed-qualitative/numeric account, explicit source/provenance, correction→save once, precise user action and education. Existing User Testing UT-VIOME-4301–4312 and Biology cases reused, not a duplicate acceptance programme.
10. **Privacy review:** Security reviews final allowed persisted schema, request/raw buffer lifecycle, temporary files/backups, storage, source deep links, audit logs, preview, exports, access control, deletion/revocation and non-consented provider connections. P0 gates apply before real-user PDF upload release; safe parser development with synthetic canaries may proceed.

## D. Crosswalk, supersession and implementation order

- UT-VIOME-4301–4312 map into VIOME-PDF-01–08 and existing UT-IMPORT-2401–2409, UT-PDF-2601–2606 and UT-TAXON-2801–2808. Reuse `shared/structured-report.ts`, `server/report-routes.ts`, `shared/report-import.ts`, existing upload path and canonical source/consent records where safe, rather than implementing a separate PDF provider engine.
- The Biology handoff's `original private attachment`, `PDF checksum`, `provider test ID in protected metadata` and original ID-retention instructions are explicitly **rejected as inconsistent with owner privacy direction**. Its rows/assay/category/date and evidence semantics otherwise stand. Similarly companion recommendation handoff's `private identity linkage` must be replaced by **user-confirmed, internally keyed, deidentified report linkage**.
- If the current Bloom source model mandates retaining a raw original PDF for provenance, architect decision is to **change that Viome-specific storage contract**. Keep only source-page references and allowed exact biological data; permit a transient browser-local PDF preview or manual re-select to verify original content. Do not retain PII even in encrypted files.
- Existing v0.5 source-fidelity bug `bloom-report-v2` round-trip and user/source permission fixes remain immediate foundational P0 work. Direct PDF Viome ingestion, deidentification and importer acceptance are **P0 v0.5** and must be completed before declaring supported Viome PDF upload operational. JSON importer remains optional. Later v0.6 research/food evidence extensions reuse imported data but never promote Viome categories into personal validated mechanisms.
- **Developer reports per slice:** input fixture type, template version, parsed category counts and ambiguity, exact implementation SHA/test/preview, persisted schema allowlist, privacy canary evidence and Security review, user-review screenshot/keyboard and actual built result, incomplete cases separately. No pass based on documenting design or on redacting output while raw originals remain stored.
