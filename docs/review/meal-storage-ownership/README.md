# ID01 individual meal storage ownership

Existing HTTP handlers already checked meal ownership. Their underlying single-record storage methods selected or mutated by ID alone. This increment requires an explicit account on every production single-meal read/update/delete and puts both owner and ID in the SQL predicate. It is storage-level defense in depth, not a claim the previous HTTP route allowed cross-account writes.

The pure injected `server/meal-records.ts` helpers back DatabaseStorage. Missing owner fails before any database call. Updates reject primary/owner field reassignment. Receipt recovery, correction, saved-template creation/recovery, retired health and deletion callers pass the signed-session owner; existing endpoint checks remain. Foreign records now resolve as not found without loading their values. If an owned correction target is deleted during analysis, the route returns404 before storing remembered ingredients or returning a false update receipt. No schema/data migration or production data operation is required.

Evidence:17 focused planner/experience/receipt/template/retired and direct-storage tests PASS; separate6 review/source/storage checks PASS (overlapping storage cases). Actual PGlite helpers prove owner predicates, absent-owner zero calls, forbidden ID/owner updates, normal clinical zero, owned deletion and preservation of the other account. Actual PUT correction route denies missing auth/foreign record/forged owner before analysis, and a deliberately deleted-during-analysis row produces404 with zero remembered writes. Existing actual App/API/PGlite correction-lost-response and encrypted saved-template review/scale/correct/save browser journeys now use these production helpers and pass, including owner isolation and320px. Types/build/source checks pass.

Scope: individual meal methods. Other parent/child storage families still require their own trace and exact negative cases; this does not close the entire ID01 ledger or independent acceptance.
