## Reuse and behavior

The existing encrypted precision-context `conditions:string[]` remains the only current condition-name store. New grouped checkbox/search UI is available in Profile → Health Profile → Medical conditions & health concerns, and the existing Biology health-context disclosure. A single reusable selector supports common labels, previous terminology (NAFLD/MASLD, NASH/MASH), distinct low-testosterone concern versus reported hypogonadism diagnosis, custom entries, removal and an explicit unknown/none-reported response. The catalogue is a versioned plain-language capture list, not a licensed clinical terminology, diagnostic classifier or evidence database; it is intentionally incomplete.

Legacy/custom strings remain unchanged and are not automatically coded or rewritten from aliases. Aliases only filter the capture options. General health-context saves no longer split existing condition names on commas. Other comma-entry fields are unchanged. Saving a condition-only edit preserves unsaved general-form fields when only the condition array changes; general context changes from other sources retain their existing refresh behavior.

No new SQL table, migration, entitlement, clinical/recommendation engine, provider, artwork or BVA ID is introduced. `conditionSource` is optional server-managed provenance alongside the same canonical name array: user assertion, opaque source revision, confirmation time and narrowly bound retry metadata. Confirmation means user selection, not verified diagnosis or onset. Per-condition clinical-status coding and first-known/effective-time migration for legacy current lists are not implemented here; existing typed GI event chronology remains separate and intact.

## Source and permission boundary

- Existing authenticated/no-store precision router owns `GET/PUT /api/precision/conditions`. The PUT replaces only the condition resource, with a strict confirmed command and source compare-and-swap. It is not a general-profile PATCH.
- `PrecisionStorage` reuses the existing account lock and encrypted profile. Reads initialize only the existing default-off source-write/privacy revision when absent; no inference permission is granted. Writes preserve current medications, goals, genetics selection, microbiome controls, sensitive sharing and all other raw context keys. Parser defaults are not persisted as newly reported facts.
- Different-account revisions fail. Concurrent/stale condition edits fail; exact response-loss retries are read back without another mutation only while their source/privacy binding is still current. Privacy change or account/source clearing invalidates old intents. Source revisions prevent A→B→A reuse. General legacy context PUT cannot erase or change newly scoped condition selections, and clients cannot forge `conditionSource` or a clinically reviewed status.
- Empty selection defaults to unknown; none-reported requires an explicit user choice. Unknown/inconsistent condition source cannot act as reviewed absence in existing nutrition eligibility. Ordinary source review/logging remains available. Wellness/private-snapshot revisions include the condition-source revision; edits and explicit assertion changes invalidate dependent private outputs. No historical disease timing is inferred from a current list or confirmation timestamp.
- The UI keeps drafts after a source conflict and reloads only explicitly. It stores no condition draft in browser storage, sends no search/selection telemetry, and invokes no AI/provider. Existing actor guards reject late responses/account changes. Request logging uses the existing static-route-only redactor; private labels are neither URL parameters nor log content. Encryption remains server-held encryption, not E2EE.
- Full context projections omit the new control metadata from legacy consumers. Public scientific research remains restricted to the existing independently approved task boundary. Selecting a name cannot authorize clinical output, change medication or lab units, grant source rights, or promote data into shared science.
