# Laboratory date revision reader

Date corrections are immutable successor observations, identified by a new record ID. The original encrypted observation is retained unchanged. This prevents date edits from bypassing planning source-ID comparisons and preserves the original date context for account export and review.

Optional strict `dateCorrection` metadata carries version1, the previous record ID and timestamp, previous entered date/time only when known, corrected entered date/time, correction time, owner reason and a request fingerprint. Corrected calendar text must agree with the canonical timestamp within the same global offset rules as original capture. Existing report context, when present, must agree too. A legacy row without an import reference remains without one; date precision and specimen association are never backfilled by inference.

The shared active-row selector excludes both unit and date superseded parents. Supported pending/confirmed and strict source-only classes retain their existing clinical boundaries. A correction replaces one active observation; it never fabricates an additional measurement or trend point. The clinical planning source guard uses the same selector, and raw-only revisions remain excluded from clinical computation.

The normal import endpoint rejects correction metadata. Generic storage insertion also denies date successors except unit confirmation carrying the exact existing source audit. Unit confirmation checks current active sources; stale pending dates cannot create a fork. Explicit entry deletion traverses both date and unit links under the account transaction lock, so deleting a corrected result cannot resurrect a predecessor. The legacy row deletion API retains its row-only contract.

Source details show the current entered date, previous stored timestamp, previous entered precision or its absence, correction time and reason. Trend points retain the audit; export retains all original records. No ordinary date writer or edit control ships in the reader batch. A dedicated owned active-source transaction, explicit review and durable receipt must be verified before emitting these fields.

Evidence: `tests/lab-date-revision.test.ts` uses actual Express/encrypted PGlite to verify strict metadata, forged import denial, active source selection, planning conflicts, stale unit denial, unit confirmation carrying audit, raw exclusion and complete deletion. `scripts/qa/lab-source-context-journey.mjs` verifies corrected/legacy dates, a single active plotted point, audit display and absence of invented import identity. Fixtures are synthetic and do not establish independent clinical acceptance.

## Reviewed date writer

`POST /api/precision/labs/:id/correct-date` requires authentication, `X-Bloom-Confirm: correct-lab-date`, a mandatory8–128 character idempotency key and strict entered date/optional time, measured timestamp, reason and `reviewed:true`. Extra fields, source/value/unit edits, future/invalid calendar context, missing review and unchanged entered context are rejected. A no-op does not rewrite an instant merely because the owner travelled to another timezone.

The owner transaction lock is shared with confirmation and deletion. Receipt lookup precedes source checks: the same source/request/key returns the original successor after response loss or later supersession. A conflicting reuse returns409. New corrections require an owned active source, create a new encrypted record with unchanged non-date facts, retain all predecessors, update existing report date context without inventing an import ID and invalidate clinical plans only for a supported confirmed input. A stale source returns409; missing/foreign returns404. An old correction retry after full lineage deletion cannot recreate the source. The client never replaces canonical state from a receipt response; it reloads the server report.

The root dialog holds a source snapshot across query refresh, requires a reason and source-review checkbox, and resets review after edits. Once submitted, request and key are frozen for exact retry. Legacy date precision starts blank. Date-only capture retains absent time; explicit local times are checked for invalid DST wall clocks. Source values/units/identifiers are read-only. The confirmation names plan invalidation and retention of the original entry.

`tests/lab-date-correction.test.ts` covers the pure successor, +14/−12/date-only/midnight/DST-gap behavior, actual owned API/transaction concurrency, receipt replay/mismatch, no-op, forged fields, stale sources, deletion retry, known/pending/confirmed/raw boundaries and preserved original payloads. The actual encrypted React/API journey additionally covers review reset, a committed response loss, exact retry, current canonical source and visible audit. The isolated Neon smoke adds correction/replay/stale-source, fresh weekly save and complete date/unit deletion without pending resurrection. No production data is used by these checks.

Repeated local collection times now require an explicit UTC-offset occurrence in both initial paste/manual capture and date correction. Spring-forward gaps are rejected; half-hour transitions are covered. A selected instant is preserved through the existing timestamp field, without adding guessed source timezone metadata. Date-only collection time remains absent. Definite typed4xx conflicts disable retry; uncertain responses retain exact-receipt retry.
