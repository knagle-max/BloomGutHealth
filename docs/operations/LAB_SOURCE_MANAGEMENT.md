# Laboratory source management

The Bloodwork tab exposes saved laboratory sources independently of clinical report availability. Whole-source deletion uses only persisted import identity, exact recorded report/specimen context and explicit unit/date correction edges. Matching dates never establish a report. Rows without import identity remain independent result sources, with their own linked revisions. Conflicting source identities joined by a correction edge fail closed. Unreadable legacy rows remain individually manageable with an unknown result count.

`GET /api/precision/labs/sources` returns opaque account-bound source references and revisions, scope, reliable counts and recorded dates, without marker values or original report identifiers. `DELETE /api/precision/labs/sources/:id` requires current `X-Bloom-Labs-Actor`, `X-Bloom-Confirm: delete-lab-source` and a strict `{revision,confirmed:true}` body. Existing shared workspace write budget applies to case/trailing-slash variants. Authenticated account-lock transactions compare the complete source version and delete the exclusively grouped records atomically. Missing/foreign IDs have the same absence response; a changed or reimported source conflicts with an older revision. Exact lost-response retries cannot remove an independent source.

Known weekly plans explicitly referencing removed records are deleted. Other source records, categories, journal entries, profile data and independent or unknown-lineage historical plans remain. Their current eligibility remains governed by canonical plan-input checks. Success resets dependent client projections even after same-account navigation; account epoch guards prevent old-account metadata restoration. Ambiguous failures refresh source and clinical projections. Unsaved form entries remain unsaved; confirmation does not clear drafts.

The generic row-only record deletion route now rejects supported and source-only lab observations. Users must use the existing logical result/revision action or the new source action, preventing older unit revisions from reappearing after a corrected row is removed. The existing result action remains separate and preserves sibling results.

No schema migration, parallel source store, date-based grouping, raw upload deletion or immediate backup-erasure claim. UI code can be reverted while retaining the safe backend route and generic deletion guard.

Verification uses actual App/HTTP/encrypted in-memory SQL: source vs independent same-date result, scoped confirmation/Cancel, stale revision, committed lost-response exact retry, reload/empty/account isolation, 320/390px, dark mode, 200% CSS zoom and keyboard focus. Focused SQL/API tests also cover full unit/date lineage, foreign IDs, new import after deletion, unknown legacy counts, inconsistent source context and independent plan preservation. Types, production build and source/API inventories are checked before publication. Independent device/VoiceOver/Design and hosted runtime acceptance remain separate.
