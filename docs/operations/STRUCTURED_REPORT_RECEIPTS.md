# Atomic structured report save receipts

The existing JSON and multipart import routes optionally accept a UUID Idempotency-Key. The authenticated account always supplies ownership. An optional X-Bloom-Report-Actor only narrows the request: a stale form whose expected actor differs from the signed-in account is rejected before writes. It never grants access or chooses an owner.

The real storage adapter derives an opaque report ID from the owner/key and compares a canonical command hash over the original source, metadata and filename. Under the existing account-erasure lock, one transaction saves the sample, bounded child batches and analysis metadata, then confirms completion. A completed replay returns the original preview before any new date fallback or writes. Changed details conflict with409; a failed child write rolls everything back. Same key under another account identifies a different report. New keys deliberately permit separate imports; this is command idempotence, not silent content merging.

Receipt version/hash lives inside the owned report and is erased with it. The raw retry key is not separately stored. Browser sample DTOs remove the internal receipt and existing raw file-path field. Report values, original source and date provenance remain unchanged. No new table, migration, provider, permission or clinical model. Legacy no-key callers retain their interface; a requested receipt with an unavailable adapter fails closed rather than using duplicate-prone legacy writes.
