# Review-service feature control step-up protocol

Component foundation only. No HTTP credential endpoint, production factory, controller grant or feature activation is installed. Current control routes remain denied. Trusted adapters must verify the actual account credential and independently provisioned `features:control` role; metadata-read permission is insufficient. A successful proof is reauthentication only, never clinical/legal approval or execution permission. Future integration must AND the lease with independent current review, scope, consent, rollout and immutable source policy.

The server issues a random signed proof after reauthentication and a fresh controller lookup. It expires within 120 seconds, binds the exact actor, session, deployment, action and normalized change (including revision, request UUID, material, reason and scope), and binds the entire current credential/grant fingerprint. A shared PostgreSQL conditional update consumes it once across replicas. Failed binding checks do not consume the original proof. A request-local lease supports the store's repeated pre/post-write authorization checks and rechecks current credential/grant state each time. It cannot authorize reads or a different change. Adapters have a two-second deadline; errors, missing tables, bad clocks, revocation and stale credentials deny without fallback.

Receipt rows contain purpose-separated HMACs rather than raw passwords, session identifiers, actors, reasons or grants. The signing secret must be explicit, at least 32 bytes and consistent across replicas; rotation invalidates outstanding proofs. Do not expose it or accept grants from request JSON. Receipts are transient authentication state, separate from immutable encrypted control audit. Expired receipt cleanup is bounded to 1,000 rows per invocation.

Migration 0014 is additive, SQL-owned and excluded from Drizzle reconciliation. CI applies it only to the isolated PR database and exercises synthetic adapters. Render's existing startup does not apply this migration. Rollback: leave the protocol uninstalled/deny routes, retain tables, and invalidate outstanding proofs by rotating the dedicated signing material through approved configuration. No destructive migration is required.

Operational limit: restoring a database snapshot within the proof lifetime could restore an unconsumed receipt. A future deployment installer must invalidate pre-restore sessions/proofs or change a trusted restore epoch/signing key before permitting writes. These tests do not establish a disaster-recovery fence or actual credential adapter acceptance.

The next trusted adapter (`feature-controller-auth.ts`, not installed) verifies the actual stored bcrypt hash, reloads the account and controller configuration after comparison, and derives the credential fingerprint itself. Server configuration must explicitly set `BLOOM_FEATURE_CONTROL_KILL_SWITCH=false`, matching `RENDER_SERVICE_ID`/`BLOOM_FEATURE_CONTROL_ENVIRONMENT`, and a single strict `BLOOM_FEATURE_CONTROLLERS` grant per account. No metadata reader or tester grant is inherited. No configuration was provisioned. Future HTTP wiring must authenticate the session, enforce shared per-account/source reauthentication budgets before bcrypt, use safe non-cacheable responses and trusted independent review facts; the adapter alone does not provide those route protections.

`FeatureControlService` composes these foundations but remains uninstalled. It binds the proof to an exact command and supplies a store authorizer that rechecks credentials and independent current review on every promotion check, including after the audit write (revocation rolls back). `reviewedCapabilityControlDecision` shares the execution evaluator's governance checks; it does not fabricate an eligible subject or waive per-user consent/rollout checks. Trusted review/source adapters default to denial. Pause/emergency-disable can restrict execution with controller proof even when promotion reviews are unavailable. Historical rollback requires an explicit immutable stored target and exact snapshot match. HTTP/shared reauthentication budgets, runtime enforcement, restore fencing, rollout monitoring and specialist acceptance remain outstanding. A stored `enabled` candidate is administrative metadata, not installed execution permission.

Action audit compatibility: the domain service writes the authenticated action into the encrypted change event and rejects a caller-supplied conflicting label before proof issuance. Historical events without this optional field remain unlabeled. Idempotency compares the complete command, so a replay cannot retrofit action metadata onto an older request. This is an additive encrypted-payload change and requires no new SQL migration.

Downgrade limit: the new reader accepts old unlabeled events; a reader predating action metadata uses a strict event schema and will fail closed on newer labeled events. Keep an action-aware reader when backing out writes. Do not rewrite immutable history to accommodate a downgrade. The running application still has no controller installer, so no live control writer was migrated.


Rollback contract: `change.rollbackRevision` is a positive historical revision no newer than the expected current revision. It is legal only for the rollback action and is included in both the signed intent and encrypted event. After proof consumption, a narrowly scoped internal history reader revalidates the same controller lease. All target control fields except the new revision/changer must match exactly, including expiry; rollback cannot extend the target's approval lifetime or silently change its cohort, scope, material, review or state. Missing/tampered/unrecoverable targets deny. Enabled restoration independently rechecks current review; paused/disabled restoration does not execute. Incident-disabled targets require the explicit emergency action. CAS and a fresh proof preserve idempotent recovery without overwriting prior events. No new migration, live route, controller grant or runtime activation is installed.
