# Reviewed Viome findings transport — bounded privacy foundation

`shared/viome-findings.ts` defines `bloom-viome-findings-v1`, a strict field-level allowlist feeding the existing canonical `bloom-report-v2` parser, owned import API and atomic receipt transaction. It is a transport for reviewed source findings, **not a native PDF extractor or a guarantee that arbitrary label/description values contain no identity**. The downstream boundary is implemented; actual PDF section/value extraction and its complete privacy canary suite remain outstanding.

Allowed fields: fixed provider/document/specimen/method types; distinct biological collected/received/reported calendar dates; explicit user source-review assertion; organism labels/provider group/reported_present, categorical assessments/descriptions, food labels/provider categories, and bounded page/column/row references to the deidentified interpretation fixture. No raw text, original bytes, filename, PDF hash, metadata bag, DOB, provider sample/test/order/client ID or unknown keys. Duplicate source positions, invalid calendars, unreviewed/inconsistent documents and unsupported versions fail with fixed errors that do not expose unknown-key names or values. Source labels remain unverified reported facts; source-review assertion is not independent science/clinical/privacy approval.

Canonical projection retains only the validated source envelope and derived qualitative rows. Canonical wrappers cannot reintroduce extra text, source-label canaries or invented abundance. No numeric score/abundance/gene/metabolite effect, allergy, exclusion, sensitive interpretation or automatic document linkage is created. Collection date alone can supply the biological test date; received/report dates cannot silently substitute. Absent collection remains explicitly import-date. Arbitrary format shape no longer identifies the provider; unattributed legacy reports say Provider not supplied.

The API rejects extra request metadata even when empty, and rejects native findings through the old multipart attachment path. Direct save and receipt storage check metadata before creating persistent objects or request hashes. Existing retry keys are internally random and account-scoped; no raw-PDF digest, cross-account dedup or date-based pairing is introduced. Legacy source retention remains unchanged; this is not a retrospective destruction or privacy certification of old imports.

The existing optional JSON review path sends only the validated envelope, clears original File/FileList and legacy identifier/note/date drafts on recognized native success/error, and shows the three biological date roles. Save depends on the valid reviewed preview, not on keeping an original file. The browser test initially caught that disabled-Save bug and the corrected path passes. This does not instruct users to convert their native PDF to JSON or expose a nonfunctional PDF picker. Native PDF-first upload→extract→repair→review→save→browse remains open and must reuse this boundary after its template/parser/value filtering is validated. No full source-template94/299 or hidden-text/XMP/end-to-end-PDF privacy pass is claimed.

Evidence: full519/519 PASS200235ms before final provider-label/copy adjustment; final21focused native field/metadata/HTTP/SQL/receipt/round-trip/crosswalk tests, types/build and actual App minimized-payload/save/reload journey pass. Tests inject synthetic unknown identity keys, raw fields, wrapper canaries, filenames, IDs/notes, future versions, bad dates, duplicate positions and numeric promotion attempts. Actual HTTP/SQL proves rejection before writes and clean owned retry storage; App uses a mocked API, while separate API/SQL tests validate persistence. Biological-value validation and PDF headers/hidden layers/error/timeout/backup/real-file privacy remain separate pending work. No near-identical screenshot gallery for this contract/state change. Public images retain their normal ungated availability.
