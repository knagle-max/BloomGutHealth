# Selected microbiome report deletion

P0-MICROBIOME-DELETE-01 implements the Microbiome portion of P0_UI_DELETE_ACCESS and P0_DELETE_SEMANTICS from UNIVERSAL_BIOLOGICAL_REPORT_MANAGEMENT_DELETION_2026-11-05.md. Baseline cd8ebdc. Bloodwork/Genetics foundations and bulk/category/unified management remain distinct approved tasks.

Every selected saved report has a visible Delete report control in Report history, independent of Viome recognition, result-detail availability, interpretation, status or selected tab. The confirmation identifies one selected source, its available date/provider/status, exclusive derived-record scope, companion and unrelated-category preservation, irreversibility and separate backup/provider retention. No unreliable observation count or provider/sample/client ID is displayed. Cancel restores focus; successful removal returns focus to Report history, selects a remaining report or shows the existing empty state. No actual user data was deleted during development.

The existing DELETE /api/microbiome/reports/:id now uses one generic owned transaction. It requires authentication, current X-Bloom-Report-Actor, X-Bloom-Confirm: delete-microbiome-report and If-Match containing the quoted deletionRevision from the owned list/result. The opaque revision describes the stored source (including owner/internal ID, content, dates/status); it is not an uploaded-file fingerprint and is never a provider identity. Same-account advisory lock and parent row lock serialize source deletion/import and FK operations; a changed source conflicts before mutation. Missing/foreign IDs return the same success/not-present response meaning only absence in the active account. A retry after committed deletion therefore converges without claiming a foreign record was erased or deleting a changed replacement.

Within that transaction, the selected source's recommendations, health impacts, metabolites, composition and analyses are removed in FK-safe order. Independently retained owned reports' nullable analysis/taxon references are unlinked, as are confirmed Viome companion links; their own findings remain. Unexpected references from another account cause full rollback rather than foreign mutation. Parent source/receipt metadata is removed last. Historical raw-file metadata pointers disappear with the row; this operation does not claim to erase separately retained filesystem/provider/backup copies. It creates no schema/migration or second deletion store.

After acknowledged success/owned absence, browser report requests are cancelled, the deleted source cache is removed, all owned report variants and dependent planning/precision/nutrition/biology/athlete projections reset. Account change/unmount cannot clear or navigate the new account from the old callback. Loss of a DELETE response retains the exact source/revision for safe retry. A stale-version conflict requires fresh list and selected-result review. Draft imports are unaffected because the control manages saved sources only.
