# v0.6 first read-only wellness context

Contract: Today must explain a saved goal using the current signed-in account's goal/profile sources even when every assay, model and optional provider is absent. Reading this view must not load raw biological reports, modify source records, imply a purpose grant or invent a source collection date. Corrections, erasure, account switching and evidence changes must withdraw or change the derived view. This first vertical is goals/constraints only; it is not the complete multimodal context or the planned action engine.

`GET /api/precision/wellness-context` reuses the existing authenticated/no-store precision boundary and only `getPrecisionContext(account)` plus `getUser(account)`. `server/wellness-context.ts` composes the existing `contextSchema`, preference schema, conservative age conflict resolver, `goalGuidance` and `goalSources`. No table, migration, separate planner, evidence catalogue, provider request or model activation. The result is typed in `shared/wellness-context.ts`; own-account `personal-wellness` is a description of existing app scope, not research, external-processing or clinical authorization.

- Missing allergy/preferences fields stay null; explicit empty arrays stay empty. Unreviewed safety stays unreviewed; Profile under18/conflicting age cannot become an adult clearance.
- Goals retain original strings and the existing unmapped fallback. Absent preferences do not create the schema's default butyrate goal. Internal legacy butyrate/diversity/athletic preferences follow existing report goal-mapping exclusions.
- `asOf` is view time only. Actual context/profile observation dates are not recorded, so `observedAt:null` and `dateStatus:not-recorded` remain explicit. Source references identify the canonical saved account settings, not fabricated assay entries.
- Source/context/evidence revisions are SHA256 fingerprints of the exact selected content and account scope. They are change detectors, not authorization tokens or original assay version IDs. View-clock advancement alone does not change content revision. Source correction, deletion, relevant profile/age, evidence or account changes do.
- Today uses the account-keyed endpoint with current source/owner/version validation. The existing planning-cache prefix handles correction/erasure invalidation; existing request-actor/session machinery rejects late foreign-account responses. Original full Biology reports and all canonical edits remain in their existing routes.

Verification: four new context/actual-router tests plus Today/age/goal/registered-admission regressions; actual App→HTTP→encrypted PostgreSQL goal correction/reload/deletion/account switch, cited Why and320/390 light/dark; existing onboarding, Today, source-pause and local-midnight journeys.
