**One execution entry point:** after reading this short file, open [NEXT_ACTIONS.md](NEXT_ACTIONS.md) for the **one current task and next eligible queue**. This file governs *how* to work; `NEXT_ACTIONS.md` governs *what* to work on. This is a consolidation of existing owner decisions, **not a new scope, release or approval policy**.

4. **[Dependency backlog](docs/operations/V06_DEPENDENCY_BACKLOG.md)**, feature-specific handoffs, existing code, CI and test receipts for implementation detail and actual state. Current repo/CI/hosted SHA is **evidence**, not inferred from a dated prose checkpoint.
5. **Archived** `CURRENT_V05_REQUIREMENTS.md`, `ACTIVE_EXECUTION_QUEUE.md`, `PERSISTENT_TASK_INDEX.md`, v0.5 RC documents, prior previews, older “first task”/project priorities and snapshots are **historical evidence only** unless a specific unresolved requirement is explicitly linked from the current active queue.

**Do not reread all large handoffs or sequentially execute every heading.** Read the exact section needed for the selected task. If old documents disagree, resolve using the above rules in one short note and proceed; do not create a new reconciliation loop.

**Roadmap/completion evidence:** Read the [v0.6 Delivery Status Ledger](docs/operations/V06_DELIVERY_STATUS_LEDGER_20261115.md) only for the selected task and current known states. When the owner requests a change or a real regression is proven, append a narrowly scoped `REVISED` delta, retaining original completion evidence. Codex updates this ledger at real state transitions—not every commit—and keeps `NEXT_ACTIONS.md` short.

## 2. Implementation and task-selection rules

- **Codex owns engineering**: inspect actual branch `enhance/bloom-experience`, PR/review and working tree; implement/test/commit/push to authorized review branch, verify applicable Render preview. Never overwrite independent local work, reset contributors or merge to `main` without appropriate authorization.
- **Exactly one active engineering slice**, with stable task ID, user-visible outcome, touched code, relevant dependencies, test evidence and measurable exit criterion. **Top of `NEXT_ACTIONS.md` is not automatically a new task**: an item already verified at current SHA is closed, even if historical prose says “continue”. An external hold is feature-scoped. Move to next independently actionable approved task.
- **Progress, not busywork**: reuse current services/assets/identity and source contracts; do not reimplement a second safety engine, AI scientific authority, lab source ledger, food database, consent system or image renderer. Don't repeatedly re-review solved source rows, unchanged fixtures, prior asset transfers or old approval debates.
- **Two materially different failed approaches** to the same blocker, or repeat failure without new evidence → record exact reproducer, attempts, safe fallback and triggering condition in the current task receipt; mark `TECHNICAL_DEPENDENCY`, continue an independent task. Do not weaken security/science or omit required assertions to escape a blocker.
- **Validation proportional to risk**: run focused relevant tests, typecheck/build as appropriate during work; full regression for shared high-risk boundaries or major integrated/release checkpoint, not repeatedly for the unchanged SHA/config/environment. A failed necessary check remains failed until corrected; never fake PASS. Once relevant tests and source audits pass, push a coherent slice, check exact CI/Render SHA once; if a remote verification is temporarily unavailable record `IMPLEMENTED_PENDING_DEPLOY_VERIFICATION` and do other independent work.
- **Concise session handoff:** `HEAD / current task+exit / completed exact SHA+tests / true blockers / next 2–3 independent tasks`. Put new results in the appropriate dated verification receipt; **do not prepend long chronological reports to `NEXT_ACTIONS.md`** or update five overlapping decision documents after every small fix.

See the existing [anti-loop policy](docs/architecture/CODEX_ANTI_LOOP_EXECUTION_POLICY_2026-11-05.md) and [risk-based testing policy](docs/architecture/RISK_BASED_CHANGE_SCOPED_TEST_EXECUTION_2026-11-06.md) for details; the concise rules above **replace competing old first-read and status-stream instructions**.

## 4. Review and authorization boundaries

**Routine approved coding, ordinary UI/design choices, scoped tests, review-branch pushes and authorized Render preview updates require no per-commit owner/Architect/specialist checkpoint.** Keep working through safe slices. Final integrated specialist/release review is tracked separately from engineering-tested status. The owner does **not** need to reauthorize a safe existing-feature fix.

**Owner review happens once at the assembled release candidate (RC), covering images, UI, functionality and performance together.** Codex may produce, revise, review, integrate and publish images to authorized development branches/preview/asset locations without seeking owner approval on each image. Use specialist design/science/rights checks and rendered QA; these are engineering quality checks, not owner checkpoints. The user provides correcting instructions only when desired; do not wait for silence to become an approval. Keep all **28 BVA requirements**, preserve historical rejected renditions and approved-image evidence, and treat rejected rendition ≠ retired requirement. Review owner corrections as precise revisions to the affected items. **Public/production release, legal/privacy/licensing and consequential clinical approval remain independently governed.** The [status ledger](docs/operations/V06_DELIVERY_STATUS_LEDGER_20261115.md) records roadmap versus actual engineering and RC state.

**Hard gates remain**: identifiable health/genetic information, account isolation, protected consent, legal/third-party source rights, consequential medical claims, paid-provider activation, destructive/production operations, `main` merge or public App Store release, and independent physical-device acceptance where required. When gated, **disable that exact function** and continue safe work; do not claim approval or deployment without proof. HealthKit authorization never implies research/Coach sharing; public cross-account research remains OFF. New functionality after v0.6 freeze defaults to v0.7.

**Truth and UX:** actual vs proposed vs performed; missing/unknown ≠ zero; complete source records, lab units/ranges, corrections and user controls discoverable through polished progressive disclosure. Keep functional routes and both light/dark, 320/390/tablet/desktop, keyboard/200% text and appropriate accessible interaction. Do not use mock biological scores or personal-effect predictions as actual facts.

## 5. When to stop or escalate

Stop only **the specific unsafe/disallowed action**; defer the blocked feature and select another safe one. When no meaningful independently actionable work remains in the current session or execution limit is reached, leave a clean exact-SHA receipt and concise remaining queue; do not manufacture further work or promise asynchronous progress.

**Do not request intermediate owner approval** for established project requirements. Request action only for an actual credential/account, paid service, sensitive data release, protected deployment or public release, native signing/device or genuine unresolved owner product choice. **Never ask for per-image or per-slice owner review.**
