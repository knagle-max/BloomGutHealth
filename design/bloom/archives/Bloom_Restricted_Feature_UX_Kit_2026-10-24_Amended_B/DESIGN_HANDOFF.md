## Design decision
**Approve clear development-only UI distinction.** Do NOT add a public-facing “restricted features” dashboard to ordinary Everyday/Athlete/Coach navigation. Approved internal reviewers may receive an isolated feature registry and preview surfaces with obvious non-colour labels and synthetic data. The UI neither grants permissions nor changes eligibility. Server rules remain Legal/Security/Codex responsibility. Design cannot make a medically regulated function safe, lawful or clinically valid.

## Requirements
**MKT-REG-1201 | P0 — Status vocabulary and approval separation.** Display `GENERAL_RELEASE` as **Candidate for general release** (never “Live” unless separately runtime verified), `HIDDEN_PENDING_APPROVAL` as **Dev only · pending approval**, `INTERNAL_RESEARCH_ONLY` as **Internal research only**, `DISABLED_INCIDENT` as **Disabled · incident restriction**. Show distinct `approval_status` separately and never infer approval from classification. **Acceptance:** Four classes distinguishable without colour; proposed vs under review vs approved clear; denied state has no misleading working CTA. **Crosswalk:** LEG-INVENTORY-903/904, LEG-GATE-801/803.

**MKT-REG-1202 | P0 — Authorized preview frame.** In isolated internal review only, use persistent banner **DEV ONLY — NOT APPROVED FOR PUBLIC RELEASE** and local label on restricted card; show synthetic-data marker, feature ID/version, outstanding reviews. A `Show development features` control is only rendered to server-authorized reviewers; it is a display affordance, never authority. **Acceptance:** no reviewer control for unauthenticated/public users; disabling preview removes restricted navigation/search/suggestions; direct API calls still denied by backend. **Crosswalk:** LEG-GATE-802/803, LEG-INVENTORY-902.

**MKT-REG-1203 | P0 — Incident-disabled treatment.** Red/muted-red state with explicit unavailable copy, no preview button, no stale cached detail. **Acceptance:** `DISABLED_INCIDENT` produces no restricted response, exports, AI output or job at any route. CSS/UI alone is insufficient. **Crosswalk:** LEG-GATE-805, LEG-INVENTORY-905.

**MKT-REG-1204 | P0 — Truthful no-access and fallback messaging.** Restricted/unavailable capability surfaces show neutral denial and safe alternatives, not unlock encouragement, self-authorization or waitlist-like guarantees. **Acceptance:** deep links and search results for unauthorized users do not reveal sensitive capability content; where appropriate return to general plans and standard journaling. **Crosswalk:** LEG-GATE-802, UT-SIMPLE-901/906.

**MKT-REG-1205 | P1 — Internal decision registry UX.** Reviewer interface: feature ID, classification, independent approval status, required signoffs, jurisdiction, evidence, code SHA, review due, incident status, approved intended use, last update. Reviewer may inspect decisions, but no ambiguous one-click “approve and ship” affordance. **Acceptance:** changes auditable; pending gates not collapsed into one badge; developer preview unrelated to production promotion. **Crosswalk:** LEG-INVENTORY-901/906, LEG-GATE-804/806.

**MKT-REG-1206 | P0 — Domain-level rather than blanket restrictions.** Lab history, general nutrition plans and educational genotype/microbiome content remain candidate mainstream experiences when their own gates pass; restricted medical interpretations and unvalidated predictions display only to authorized reviewers. **Acceptance:** no blanket concealment of safe features due solely to neighboring restricted feature; no forbidden prompt or action through general AI. **Crosswalk:** LEG-LAUNCH-701/703/704, LEG-INVENTORY-902.

## UX examples and negative cases
1. Internal reviewer previews AI photo logging: amber banner + approvals outstanding, synthetic food only, no automatic public activation.
2. Internal research on microbial flux: purple research label, synthetic/test inputs, not measured metabolite values.
3. Incident-disabled metabolite scores: no preview access; no cached result or working action.
4. Ordinary user opens a shared restricted URL: no capability details or health data exposed, safe return to supported feature.
5. Ordinary user uses lab trends while lab-derived treatment interpretation remains gated: no blanket suppression.
6. `GENERAL_RELEASE` row with `PROPOSED` approval: clearly not enabled just because category is general.
7. Reviewer changes environment or loses authorization: preview disappears, backend still denies restricted processing.
8. Non-Canadian environment: jurisdiction-specific restrictions cannot be overridden by front-end controls.

## Amendment A — Authorized graphite development toggle (2026-10-24)
**Source:** Chief Architect clarification on the development-only preview switch, received 2026-10-24. **Supersedes:** any earlier visual proposal implying that amber/purple should be the background of the toggle itself, or that a client-side toggle can reveal every hidden capability. It does **not** supersede the existing release-category badges or any Legal requirement.

**MKT-REG-1207 | P0 — Discreet graphite toggle; unmistakable classification.** The `Show development features` toggle uses the shared neutral graphite/charcoal skin (#343B43 / #252B32), with visible ON/OFF state, clear accessible name, 44px touch target and keyboard/focus support. The switch is rendered **only after server confirmation** of an authorized reviewer in the correct environment. In the adjacent preview list, each authorized capability retains a readable category label: `Dev only · pending approval` or `Internal research only` as returned by the server. Colour alone is never the distinction. The development preview's global `DEV ONLY — NOT APPROVED FOR PUBLIC RELEASE` identification remains available in-context, not necessarily a full-width bright banner.

**MKT-REG-1208 | P0 — Eligibility-filtered preview and incident hard stop.** Toggling ON can display *only* capabilities in an allowlist returned for the current authenticated tester, applicable environment, jurisdiction and purposes **by the server**. Neither the toggle, React state, a URL parameter, local storage nor CSS is a privilege source. `DISABLED_INCIDENT` must never be included or previewable by the ordinary reviewer toggle, regardless of past cached visibility. A preview-denied, authorization-expired or wrong-environment response must hide or disable the surface without leaking restricted payloads. P0 gate is in **server/API/AI/jobs/export enforcement**, not visual components. UI merely renders a server-authorized projection. The mode cannot bypass clinical, research/REB, legal or other restrictions.

**MKT-REG-1209 | P0 — Separate reviewer classification and approval state.** A category (`GENERAL_RELEASE`, `HIDDEN_PENDING_APPROVAL`, `INTERNAL_RESEARCH_ONLY`, `DISABLED_INCIDENT`) is distinct from approval workflow (`PROPOSED`, `UNDER_REVIEW`, `APPROVED`, `REJECTED`, `SUSPENDED`) and deployment exposure. For each preview item show classification and, on expansion, unmet requirements/approvals without disclosing confidential reviewer-only material to the wrong role. Do not show a public-available checkmark solely for `GENERAL_RELEASE`. All access and eligibility resolved by the authoritative registry; the gate is P0 architectural Codex work, not merely branding polish.

**Acceptance / test fixtures (Architect and Codex):** (1) authorized dev in isolated environment toggles ON and sees exactly their server-allowed pending/research list; (2) a different tester sees a strict subset; (3) wrong environment and unauthenticated reviewer get no toggle and no restricted API response; (4) incident-disabled feature stays unavailable even when switch ON; (5) role revoked mid-session invalidates list and any related API/job/export access; (6) approvals pending do not become public upon code deployment; (7) access blocked after direct URL, tampered client state and AI tool calls; (8) screen-reader announces toggle label/state and item status; (9) keyboard, 320px, 200% zoom, light/dark have readable contrast. These are **required tests, not tests already run**.

**Status at amendment:** Legal registry and implementation instructions reported committed by Chief Architect; Codex still must map registry to actual functionality, implement fail-closed enforcement, test authorization and verify Render. No claim that any of these runtime gates currently work. Branding asset `development_toggle_graphite.svg` added as an editable, synthetic internal UI reference. `design-tokens.extension.json` now includes `developmentToggle` neutral tokens. Architecture remains v0.5/v0.6 cross-cutting P0; do not interrupt unrelated v0.5 execution unless an independently verified urgent defect warrants it.


## Amendment B — Production-positioned preview and responsive removal (2026-10-24)
**Source:** Product owner clarification: restricted capabilities are positioned in their **real intended production layout** when shown to an authorized developer; switching OFF removes their entire rendered layout footprint. **Supersedes:** any interpretation of `preview_desktop.svg`, MKT-REG-1202 or Amendment A suggesting that a dedicated feature gallery, separate preview-only dashboard, permanent placeholder or overlay is the primary experience. An internal registry may still exist for governance, but it is **not** the main feature presentation. Preserves Legal's classifications, fail-closed server enforcement and incident-disabled hard stop.

**MKT-REG-1210 | P0 — In-situ production-layout preview.** Each authorized restricted capability mounts at exactly the same component position, navigation hierarchy and responsive breakpoint that it would use when public, with its normal information architecture and intended working interactions (subject to server-authorized synthetic/test data, clinical restrictions and mocks where a backend is not ready). Development-only elements adopt a restrained graphite/charcoal treatment for their outer treatment, subtle accent/border or header; do not repaint all data visualizations or transform brand and semantic colours into graphite if that would corrupt clinical/evidence semantics. Each feature displays an unobtrusive readable label `Dev only · pending approval` or `Internal research only` plus an accessible explanation and available approval details. Preserve Everyday green, Athlete blue, Coach indigo in surrounding live functionality. **Acceptance:** With authorized toggle ON, restricted feature has the same placement, width, tabs, reading order and task context intended for release; graphite tint is distinguishable but quiet, status is not colour-only. The distinction must remain on relevant nested views/exports in authorized testing.

**MKT-REG-1211 | P0 — True removal and automatic layout reflow.** With toggle OFF, restricted features are **unmounted/absent**, not `visibility:hidden`, opacity 0, disabled skeletons, empty cards or reserved grid columns. Navigation entries, tab counts, separators, section headings, search suggestions, actions and downstream links that exist *solely* for restricted capabilities disappear as well. Adjacent allowed UI reflows into remaining space using the application's real responsive layout. Exception: if a public explanation or unavailable message is separately approved, it is a distinct general-release capability—not a hidden restricted feature leaving a placeholder. **Acceptance:** A dashboard grid collapses from three cards to two without a blank third slot; a sole restricted panel removes its header/divider; empty navigation groups disappear; mobile stack has no void; no broken active tabs, inaccessible focus, stale selected route or accidental duplicate content on toggle changes. `display:none`-style omission is acceptable only as a presentational result; component and underlying sensitive data must still be denied by server and not preloaded.

**MKT-REG-1212 | P0 — Auth changes, focus and state continuity.** Visible preview set is the intersection of server-authorized feature IDs for *tester, role, environment, jurisdiction, intended purpose, live approval/restriction state*, and the local `showDevelopmentFeatures` preference. Toggle cannot add anything absent from server allowlist. `DISABLED_INCIDENT` is always excluded. Turning OFF cancels/invalidates restricted requests and clears restricted client-held data per security policy; draft retention is governed by existing policies and must not leak into public screens. If focus was within a removed feature, move it to a stable logical target and announce the change for assistive technology. If user is on a restricted deep-link when permission expires/toggle OFF, redirect to the closest permitted parent and preserve only permitted context. Restore normal layout without full reload when safe, and never expose restricted data through prefetch or cached route state. **Acceptance:** toggle ON/OFF in desktop/mobile, live role revocation, server permit subset, direct URL, cached panel, empty section, screen-reader focus, scroll restoration and incident override regressions pass; all actual enforcement is Codex/Security's responsibility.

**MKT-REG-1213 | P1 — Reusable layout contract, no duplicate prototype UI.** Codex should wrap the **actual production-intended** component with an authorization-aware boundary rather than maintain two divergent 'live' and 'dev' versions. Development graphite chrome and status label are a wrapper applied only while capability is restricted and previewed. Promote to approved general-release via server policy without changing content geometry, component identity, underlying business rules or app navigation. **Acceptance:** side-by-side synthetic snapshots of permissioned ON and OFF demonstrate stable surrounding UI and no layout gaps; feature promotion removes wrapper while preserving same component position. Developer/tester labels never imply clinical validation, entitlement or production availability.
