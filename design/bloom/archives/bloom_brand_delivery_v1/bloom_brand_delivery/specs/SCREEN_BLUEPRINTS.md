# Screen blueprints — Proposed

## 1. Today (Everyday)
**Hierarchy:** top bar (logo, mode, settings) → greeting + one specific next action → compact daily nutrition status → today's entries → relevant next-meal suggestions → optional deeper learning. Repeated “Log meal” buttons should not compete for hierarchy.

**First-run state:** “Build your first food snapshot” + Log your first meal; secondary “Explore how Bloom works.” Avoid empty numeric rings or predictive gut health claims.

**Returning state:** one single actionable suggestion **only when supported** by actual stored goals/evidence; provide “why this?” without making user read the mechanism first. If personalization unavailable, useful generic logging guidance.

**Nutrient cards:** units and provenance, e.g. “Protein · 56 g logged · includes 3 of 4 meals with known values.” Avoid “56 g / target achieved” with incomplete data.

## 2. Explore (Everyday)
**Hierarchy:** food search → selected food overview in plain English → personal relevance or clear unavailable state → “How it connects” flow → evidence/citations disclosed on demand. Use a simple readable linear path before any graph/network visualization. Foods, nutrients, microbes, pathways and outcomes retain different entity categories.

**Evidence chips:** “Measured in your report” only for reported measurements; “Tested in people,” “Observed association,” “Biological mechanism,” “Food composition” for research; “Used in your recommendation” only when actual rule participates. These are not interchangeable confidence scores.

## 3. Progress (Everyday)
Use explicit, source-dated observations. Group nutrition habits, user-reported symptoms, labs, and microbiome reports separately. Never visually imply causal effects from temporal correlation. Prefer “Not enough comparable data yet” over invented trend. All charts must have labeled units and meaningful baselines.

## 4. Log food
Entry paths: Search / Scan / Type / Photo (when enabled) → review matching product/portion → save → confirmation or correction. Preserve barcodes and serving unit; show edit before commit. Camera-denied state should keep manual input prominent. Mark absent nutrient values as unknown, not zero. Make photo provider consent separate from local barcode scan.

## 5. Athlete
Deep-blue shell using same type/spacing system as Everyday. Prioritize today’s training load, planned session fueling, hydration observation, recovery journal. Avoid red/green judgment on training readiness absent validated measurement. Clearly identify observations as self-reported and supplement certification checks as self-reported (not independently verified).

## 6. Profile/privacy
Single approachable section “Your data & choices”: data sources, per-connection scope, export, deletion, privacy information, optional AI-photo consent. Warning language should be descriptive, never coercive.

## Responsive and accessibility
Small screens 320/390px: single content column, no horizontal clipping, tap targets >=44px, inputs >=16px, bottom navigation safe-area spacing. Wider screens 768/1440px: reading lines ~65–80 characters, grids where comparison genuinely helps. WCAG 2.2 AA as target; verify contrast, zoom to 200%, keyboard focus and dialogs; reduced-motion preference respected. Do not use a hard-to-read 9–10px uppercase label for essential information.
