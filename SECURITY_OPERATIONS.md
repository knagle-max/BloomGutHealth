## Request policy and shared budgets

Cookie-authenticated API mutations (including login/logout/signup) require an exact Origin match. Without Origin, only `Sec-Fetch-Site: same-origin` is accepted. Cross-site and sibling-site metadata are denied even with a supplied Origin. The application never substitutes forwarded-host values for Host. Render uses one trusted proxy hop. Optional `APP_ORIGIN` pins the externally visible scheme/host/port; configure the exact origin without a trailing slash. Browser fetch and multipart uploads supply Origin normally. Non-browser mutation clients must supply the expected Origin; cookie possession does not bypass this policy. CORS is not an authorization mechanism.

All replicas use the PostgreSQL request_budgets table, an atomic upsert and database time. Authentication is limited to 60 attempts/source and 20/account per 15 minutes; resource actions to 120/source and 30/account per minute. Covered paths include upload/import, analysis, recipe/coach/planning/photo/transcription and exports. The source budget is checked first. Account and address keys are HMAC-SHA256 digests with the shared session secret; raw identities are not retained. Accounts share the login/signup budget to avoid alternate-route bypass. Local auth/resource guards remain additional controls. A shared-database failure returns 503, never a weaker per-instance fallback. Limits expire; denied requests do not extend windows. Bounded cleanup removes expired rows each minute; active identities keep one row per budget. Quantitative legitimate-user false-positive testing remains open.

Migration 0006 is additive and idempotent. Startup also ensures this table/index, matching the existing session-store startup pattern. CI tests schema creation and concurrent limiter objects with embedded PostgreSQL; production-app CI exercises the real PostgreSQL transport. Do not replace this with process memory when adding replicas. Rollback can retain the unused table.

## Upload/service boundary

Only JSON/CSV reports enter the Express importer. Multipart content is bounded to 2 MiB, one file, four small fields and five parts, held in bounded memory rather than staged on disk. UTF-8 decoding is strict; actual JSON/CSV structure and report schema must pass. JSON has depth/node limits; CSV has a 1,000-taxon row bound. Compressed formats are not accepted or decompressed. Malformed, oversized and raw-sequence inputs are rejected. This reduces the active attack surface; it is not malware quarantine or resource-isolated raw processing. Aggregate concurrent-upload memory/CPU testing is outstanding.

The Python upload path is disabled in authenticated middleware before multipart parsing; no raw-file processor is activated. Analysis refuses server paths and only handles structured reported percentages. Express sends only the required taxa/percentages and nonidentifying processing placeholders, not account identifiers, notes or whole report content. Bearer authentication remains mandatory. Private-network placement/token rotation verification is still an operational release requirement. Historical raw-file paths are withheld from sample APIs but are not erased from storage by this change.

## Encryption/key rotation

Legacy version-1 records remain readable using PRECISION_DATA_KEY. No existing key is changed in this release. To prepare rotation, put base64 32-byte keys in the hosting secret store as a JSON map in PRECISION_DATA_KEYRING and select a safe identifier using PRECISION_ACTIVE_KEY_ID. Version-2 envelopes record the identifier and bind version, key ID and user ID in GCM AAD. Missing, wrong, malformed or tampered keys/envelopes fail closed. Never commit or print either configuration.

Rotation procedure: verify a protected backup and restore in isolation; provision old/new keys through a managed secret store; stage the ring and active ID together; test legacy and new reads; re-encrypt records in an independently reviewed, resumable transaction/batch migration; verify counts and decryption after restore; retain prior keys until old ciphertext and protected backups expire. This pass supplies format support and tests, not the production re-encryption job, managed KMS deployment, actual key rotation or backup drill.

**SEC-08 distinction:** Individual account erasure, a disposable **development DB reset**, and a privacy-driven expiry/deletion/backup restore have different semantics. Scientific knowledge need not reside in a separate physical database; an **independent immutable reviewed nonpersonal release + tested clean restore and account-free promotion/withdrawal controls** can meet the boundary. “Deidentified” does **not** automatically mean nonpersonal and approved for redistribution, and a synthetic test's successful prediction is **not** permission to promote its result. Shared knowledge must survive an ordinary test-account wipe **if and only if** it is properly independent, reviewed, rights-eligible, reproducibly backed up/restorable and not withdrawn. **Do not implement a shared knowledge system solely to pass the audit**; report current gaps. No test-specific data, source samples, private prompts or derived user conclusions in shared releases; a restored older release cannot undo newer scientific withdrawals.

1. **Demonstrated critical vulnerability/missing safeguard** → existing **P0 only when reproduced**, smallest existing-control repair, exact affected path and proof; serious credible suspected risk escalates for targeted verification without falsely claiming exploitation.

## 2026-11-21 — Runtime minimization and future E2EE/recovery interpretation (SEC-01..08 refinement)

**STATUS: REQUIREMENT / AUDIT INTERPRETATION ONLY — no code, deployment, operator verification or new security mode established.** Fold into the existing bounded SEC-01–SEC-08 read-only audit, existing `PRIV-S0..S5` threat tiers and G1–G5 readiness. No new scores, trackers, security framework, implementation lane or immediate real-data activation. Assess **actual** code and user-visible behavior, not assumptions from this design memo.

1. **SEC-04 logs, errors, crash/telemetry:** Trace all *actual* central logger/formatter, HTTP error, job/worker, browser/telemetry and vendor transport boundaries. Enforce value-minimized logging before any sink where implementation supports it, with strict deny-by-default fields and no raw biomarker values, diagnoses/hormones/medications, genome/biome content, free-text notes, VOI answers, full request bodies or key material. Audit metadata is meaningful **without** sensitive before/after values: pseudonymous event/opaque correlation reference, operation, time and source revision only when purpose/retention/authorization permit. **Do not assume one logger controls every sink** or put raw account IDs/health facts in log or trace keys. Presentational low-number/Gentle mode is NOT a confidentiality feature. Code/config/CI/local/target environment evidence remain distinct.
2. **SEC-01/02/04/05 caches and jobs:** Find the real cache and queue owners before adding any wrapper. Use actual account/purpose/permission and source/revision/claim-policy-bound membership when applicable; opaque/HMAC-scoped identifiers where keys may reach operational telemetry. Do not treat cache-key scoping as authorization: recheck server ownership and current source/consent at use/presentation and final asynchronous publish. Avoid personal payload duplication, set bounded retention, purge/invalidate dependencies after corrections, logout where appropriate, consent withdrawal, rights retraction, account erasure and clean restore; decline stale results. Unknown cross-process/provider cache behavior → `NOT VERIFIED` rather than invent an eviction guarantee.
3. **SEC-06 outbound investigation:** Keep independent public **nonpersonal reviewed evidence discovery** separate from private account reasoning. Minimize requests by purpose and approved provider policy; no hidden identifier, longitudinal profile, user-genotype, private note or free-text transfer to public scientific research calls. Stripping names alone does **not** make uniquely identifying health histories nonpersonal. A supposedly consented private cloud call remains **DENIED** unless the specific personal provider processing permission, privacy terms, retention and transport gates are actually approved. Schema/eligible review and source authority govern returned hypotheses and optional `VOI-I..M` categories; outages fail closed with no sensitive diagnostic echo. Don't assert an installed private LLM provider from a synthetic runner.
4. **SEC-01/03/05 canonical lifetime and retention:** Authenticated server-derived account ownership on each existing reader/writer, minimal transient artifact creation, bounded provider/upload/export retention and no unintended shadow medical response store. Distinguish primary transactional erasure (already implemented for important owned tables) from separately unverified caches, uploads, queues, provider retention, logs, protected backups and post-restore tombstones. A raw account export downloaded by the user cannot generally be remotely erased; describe the real limit. Retaining reviewed nonpersonal science across a test-account reset requires release isolation/independent clean restore, and must not reintroduce personal fixture data or revoked science (SEC-08).
5. **PRIV-S0..S3 future trust models:** Current `bloom_cloud` decrypts account records in its authorized server process under server-managed keys—**not zero knowledge or E2EE**. Future `local_private`, customer gateway and `client_e2ee` remain synthetic/research designs until specific independent security, physical-device, source/endpoint, migration and environment gates. A gateway operator may access plaintext unless independently protected. Genuine client-held E2EE cannot guarantee confidentiality against endpoint compromise or malicious server-delivered web JavaScript; evaluate native signed-client trust and update supply chain as separate threats. Keep metadata leakage, private access-pattern disclosure, device compromise, backups and support tooling in the trust map.
6. **Recovery and key custody — future S3 acceptance, not near-term implementation:** Distinguish authentication keys from encryption keys; examine user-held recovery secret, trusted-device continuity, secure hardware/keychain and explicit server-assisted/escrow recovery as alternatives. Recovery relying on Bloom/server decrypt authority weakens a strict zero-knowledge claim; honest UX must disclose it. Pure user-held recovery risks **irreversible loss** if all keys/recovery factors vanish. Multi-device enrollment, removal, key rotation, credential changes and backup/restores must not silently grant Bloom decryption or break historical records. Hardware-protected/synced/passkey-backed recovery inherits platform-specific trust and cannot be assumed equivalent to wholly user-held keys. Never claim E2EE or recoverability until recovery, compromise, device-loss and migration tests pass independently on the actual supported client.
7. **Rollout discipline:** First **audit** real existing logging/errors, cache/jobs, outbound routes, account-scoped source and deletion boundaries under the strict read-only SEC audit. Classify each `VERIFIED / PARTIAL / MISSING / NOT TESTED / NOT APPLICABLE` with exact code/test/evidence scope and minimal repair. Only reproduced urgent P0 issues supersede current P1/P2; otherwise make narrow source-safe fixes when eligible, not a blanket “security hardening sprint”. Never treat auditing the future E2EE plan as a demand to build or activate it.
